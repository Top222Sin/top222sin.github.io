SVE 三件套极致优化：矩阵乘 / FFT(变换) / 编解码 —— NCNN、MNN 的 ARM 后端就是这层

配套文件：neon_l3_sve_kernels.cpp（可运行实验台：GEMM SVE2 8×VL / FFT radix-4 蝶形 / requantize SVE2，均带标量对拍）

浏览器预览：neon_l3_sve_kernels_diagrams.html
真实代码锚点（均来自本工作区）：

〇、先定位”这层”在哪

你说”NCNN、MNN 的 ARM 后端就是这层”——精确说，是推理引擎的底层微内核层（ukernel layer）。引擎上层做图调度、内存管理；真正吃满芯片算力的是最底那一层：GEMM、卷积变换、量化(编解码) 的几个手调内核。这层在 NCNN 里是手写 NEON，在 MNN 里已整层委托给 Arm 官方 KleidiAI（它的 kai ukernels 同时提供 NEON / SVE / SVE2 / SME2 多档内核）。





一、矩阵乘（GEMM）—— 后端最热调用

GEMM 占推理 90%+ 算力。两家的落点：

  • NCNN：手写 NEON。fp32 微内核在 gemm_arm.cpp（8×4 块、fmla rank-1 更新），int8 在 gemm_int8.h（SDOT 微内核，16 个 int32x4 累加器）。本工作区这版还没有 SVE——正是第四部分讲的”逐代 NEON 手写”。
  • MNN：cmake/KleidiAI.cmake 直接拉取 Arm 官方 KleidiAI，其 kai ukernels 把 GEMM 做了多档分代：
    • matmul_clamp_f32_qai8dxp_qsi4cxp/*dotprod.c / *i8mm.c → NEON（dotprod / i8mm）
    • .../*sdot.c / *sdot_asm.S → SVE2（svdot 向量长度自适应；注意**基础 SVE 没有 svdot**，int8 矩阵乘需 SVE2）
    • .../*mopa.c / *sme2_mla.c / *sme2_dot.c → SME2（外积/矩阵指令，更大吞吐）
    • 编译旗（KleidiAI.cmake 实摘，分两档）：NEON 档 -march=armv8.2-a+i8mm+dotprod+fp16；SVE/SVE2 档 -march=armv8.2-a+sve+sve2（注意：该旗标不代表 SME2——SME/SME2 需独立架构扩展与工具链支持，且”两档”的准确语义以实际版本源码为准）。

⚠️ 本部分 §一§三 的 FP32 GEMM / FFT / requantize 三件套只用基础 SVE 指令（svld1/svmla/svwhilelt/svst 等），所以支持 SVE 的核（V1/X2/V2/X4 等）跑同一份 VLA 源码。概念澄清：V1 是 Neoverse V1 核心名；VL（向量长度）是实现参数——VL=8 只表示 FP32 8 lane = 256-bit（V1 的典型实现），不是 SVE 的通用事实（SVE 支持 1282048-bit）。SVE2 在这些 FP32 路径上兼容、不引入新指令；SVE2 真正的增量是 int8 svdot 矩阵乘（即 KleidiAI 的 *sdot 档，以及 int8 GEMM/量化），基础 SVE 并没有 svdot。注意：SME2 需要独立架构扩展与工具链（-march=armv8.2-a+sve+sve2 不代表 SME2）——KleidiAI.cmake 中”两档”旗标的准确含义以实际版本源码为准。

这正是第四部分”SVE/SVE2 一份内核跨核”的工程现实版：KleidiAI 用同一套 ukernel 源码，靠编译旗与运行时分发，在 NEON/SVE2/SME2 三代核上全自动选路。你自己写引擎时，最务实的做法就是直接复用 KleidiAI（或参考它的 ukernel 布局），而不是从零手敲汇编。

二、FFT / 变换 —— conv 的”编解码”

NCNN 的卷积并不用 FFT（视觉模型用 Winograd/im2col 更划算），但**Winograd 变换本身就是卷积版的”编码→逐点乘→解码”**，角色与 DSP 里的 FFT 完全同构：

  • conv3x3s1_winograd23_transform_kernel → 编码权重进 Winograd 域（预计算，一次）
  • conv3x3s1_winograd23_transform_input_tile → 编码输入 tile
  • 在变换域做逐点乘（变成小 GEMM）
  • conv3x3s1_winograd23_transform_output_tile → 解码回像素域

这就是”编解码”在 conv 里的真身。换成真 FFT（音频/DSP/kissfft/CMSIS-DSP），SVE2 的写法极其顺手：

svld2/svst2 直接完成复数据的解交织/交织，省掉 NEON 里那串 vtrn/vuzp 搬弄；svwhilelt_b32 掩掉 n 非 4 倍数的尾部，免写 remainder——与第四部分谓词消除尾部一脉相承。

NCNN: transform_input → 变换域乘 → transform_output
FFT: fft_forward → 频域乘 → fft_inverse
SVE2 写法：
svld2 拆 [re,im] 成两向量 → 分量级复数乘加 → svst2 写回
svwhilelt 掩尾部，零 remainder 循环
锚点：ncnn convolution_3x3_winograd.h: transform_kernel/input/output

四、三件套串起来：一份 SVE2 后端该长什么样

内核 后端角色 NEON 现状（NCNN 手写） SVE2 改写（MNN/KleidiAI 路线）
GEMM 占 90% 算力 gemm_int8.h SDOT，逐代手写 复用 KleidiAI kai ukernel，*sdot 一份跨 X2/V1/X4/SME2
变换 conv 的编解码 transform_kernel/input/output Winograd svld2/svst2 解交织复数 + 谓词尾部（FFT 同理）
编解码 int8 量化往返 requantize_arm.cpp vdupq/vmulq svmul+svcvt+svqxtnt 饱和窄化，fuse 进 GEMM

工程结论（你真正该带走的）：

  1. NCNN 这版还是手写 NEON（无 SVE）；MNN 已经把整层后端交给 KleidiAI，后者用同一套 ukernel 源码 + 编译旗，在 NEON/SVE2/SME2 三代核上自动选路。
  2. 你自己要做的”SVE 极致优化”，最务实的不是从零写汇编，而是照 KleidiAI 的 ukernel 布局写 VLA 内核 + 谓词尾部 + 运行时 HWCAP 三路分发（第四部分已讲），再 fuse 量化。
  3. FFT 与 Winograd 变换是”编解码”的两种形态：前者服务 DSP/音频，后者服务视觉 conv；基础 SVE 的 svld2 解交织 + 谓词，对两者通用（V1 即可跑）。
  4. 第四部分的”VLA + 谓词 + 三路分发”在这里闭环：它就是你写一个能跑在 V1(X2 基础 SVE)/X2/V2/X4( SVE2)/Neoverse 上、且自带 GEMM+变换+量化三件套的推理后端内核所需的全部底层能力。

一句话：NCNN/MNN 的 ARM 后端这层 = GEMM + 变换(FFT/Winograd) + 量化(编解码) 三个手调内核；SVE/SVE2 让它们从”每代一份 NEON 汇编”升级为”一份 VLA 内核跨 V1→X4 多代核”（FP32 路径基础 SVE 即够，int8 矩阵乘才需 SVE2 的 svdot），而 MNN 已用 KleidiAI 把这条路走通了。
