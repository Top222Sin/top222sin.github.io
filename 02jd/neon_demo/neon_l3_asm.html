一、为什么不在 intrinsics —— 分水岭在哪

L2 用 <arm_neon.h> intrinsics：你告诉编译器「我想干什么」，寄存器分配、指令顺序、是否 spill（溢出到栈）全由编译器决定。对绝大多数热点这已经足够，且安全。

L3 手写汇编：你自己决定每条指令、每个寄存器、每个周期。分水岭只有一个——微内核被调用的频率。

一个 GEMM / Conv 微内核（比如 gemm_transB_packed_tile_int8_asimddp）在跑一个 ResNet 时会被调用上亿次。编译器在保守分配下带来的任何一处浪费：

  • 一次 spill（寄存器不够、被迫存栈再取回）→ 多一次内存往返；
  • 一条多余的 vst / 重排指令；
  • 一个没排好的依赖停顿（后一条指令干等前一条的结果）；

在「上亿次/秒」的放大下，都会变成肉眼可见的慢。而这些靠 -O3 消除不了——因为编译器不敢假设你愿意牺牲可读性与可移植性去钉死寄存器。

ncnn 的实锤：同一份 GEMM 同时保留 intrinsics 版与手写汇编版，用宏切换：

结论：先 intrinsics 跑通正确性，再对「真·热」的微内核下沉到汇编微调。这是工程取舍，不是炫技。

二、寄存器分配（Register Allocation）

2.1 棋盘有多大

  • AArch64：32 个 128-bit V 寄存器（V0–V31）。
  • AArch32：只有 32 个 64-bit D（或 16 个 128-bit Q0–Q15）——这正是 gemm_arm.cpp 里那份 aarch32 内联汇编用 q0–q2 / d0–d7 的原因，架构不同、棋盘更小。

2.2 AAPCS64 调用约定决定的「免保存区」

这是 ncnn 故意利用的关键：

区间 保存责任 叶子函数里
V0–V7 调用方保存（参数/返回值） 随便用
V8–V15 被调方保存 用了就得 stp/ldp 压栈恢复（有开销）
V16–V31 调用方保存 随便用

2.3 ncnn 的分配账本（见图一）

  • 累加器 → 全用 v16–v31（16 个 int32x4 = 64 个部分和 → 8×8 输出块的一个切分）；
  • 数据块 A/B → 用 v0–v7（载入 tile）；
  • v8–v15 → 故意留空！不是忘了，是为「不付保存代价」主动让出的 8 个槽。

效果：整个微内核零寄存器保存/恢复，纯叶子效率。那 8 个 free 槽不是闲置浪费，而是「为了不付 stp/ldp 代价而主动放弃」——这是库开发者才会抠的细节。

V0–V7 调用方保存（自由）
V8–V15 被调方保存（要 stp/ldp → 躲开）
V16–V31 调用方保存（自由）

V0 V1 V2 V3 V4 V5 V6 V7 V8 V9 V10 V11 V12 V13 V14 V15 V16 V17 V18 V19 V20 V21 V22 V23 V24 V25 V26 V27 V28 V29 V30 V31

ncnn int8 内核的实际用法
· 累加器 v16–v31（16 个 int32x4 → 8×8 输出块的 64 个部分和）
· 数据块 A/B 用 v0–v7（载入 tile）
· V8–V15 故意留空：用了就得保存/恢复，付代价 → 主动让出

★ 输出块尺寸 = 寄存器账单逼出来的 块再大 → 累加器数 > 32 → 溢出(spill)到栈 → 直接慢一个数量级。 所以「这个 GEMM 算 8×几的块」不是数学选择，是预算决策。

2.4 输出块尺寸 = 寄存器账单逼出来的

块再大 → 需要的累加器数 > 32 → 溢出(spill)到栈 → 直接慢一个数量级。所以「这个 GEMM 算 8×几的块」不是数学选择，是寄存器预算决策。ncnn int8 选 16 个累加器（8×8 切分）、fp32 选 8 个累加器，正是这个权衡的落点。

2.5 内联汇编里「钉」寄存器（见 gemm_arm.cpp:2455 约束表）

"2"(_sum0) 的含义：让这个输入操作数使用和输出操作数 #2 相同的物理寄存器，从而跨 asm 块把累加器钉死、不挪窝。配合 "memory" 告诉编译器内存被改、"v0".."v3" 声明这些寄存器被踩了。

三、指令调度（Instruction Scheduling）

3.1 两个独立指标

Cortex-A 系列是超标量、乱序内核（A72 双发射，A76 每周期可发 2 条 ASIMD + 1 条 load）。每条指令有两个独立指标：

  • 延迟 latency：结果多久后能被下一条指令使用（FMLA 约 4 周期）；
  • 吞吐 throughput：每周期最多能发几条同类指令（FMLA 约 2/周期）。

陷阱：如果你写的是依赖链——fmla 的结果直接喂给下一条 fmla——那下一条必须等 4 周期，吞吐被压到 0.25×（见图二左）。

3.2 解法 = 更多累加器（ILP 深度）

这就是为什么 int8 内核要 16 个累加器（v16–v31）、fp32 内核要 8 个累加器（%2–%9）。看 gemm_int8.h:10021 那一串：

这 16 条 sdot 彼此互不依赖——v16 的结果还在「飞行」中（等它的 4 周期），后面 15 条已经排队发射出去了，流水线被填满（见图二右）。累加器的数量 = ILP 深度 = 你能重叠多少条独立指令来掩盖延迟。

累加器的数量 = ILP 深度 = 你能重叠多少条独立指令来掩盖延迟 低于这个数，内核就在空转等数据。ncnn int8 用 16 个、fp32 用 8 个，正是这个权衡。

3.3 预取调度：把访存藏到计算后面

看 fp32 内核 gemm_arm.cpp:2456 开头的顺序：

prfm 在 ld1 之前就发出，且地址提前了 #128/#256 字节——目的是等 ld1 执行时，数据早已在 L1 里了。这是手工调度才能精确控制的（编译器自动 prfm 往往距离/时机不够准），直接接回你 profiling 篇的「memory-bound 就查对齐/预取」。

3.4 循环尾调度技巧（最容易被忽略）

注意 gemm_int8.h:10037 这段：

subs（设分支标志）和 bne（吃标志）本可紧挨着，但作者故意把 subs 插在 sdot 流中间、让一批独立 sdot 在它之后继续发射。因为 subs 的结果（标志位）1 周期就就绪，bne 可以「在途」等待，而此时流水线继续发后续 sdot——避免了循环尾部流水线排空。这是教科书级的依赖调度，编译器几乎不会自动为你做。

3.5 手写汇编的两种形态（对照 CUDA 的 PTX/SASS）

  • 内联汇编（ncnn 选的）：asm volatile(...) 嵌在 C++ 里，编译器管外围函数/ABI，你只控热块。代价是约束（"=w"/"=r"/"memory"/"v0"）繁琐，且编译器仍可能在周围做点你意料之外的事。
  • 纯 .S 文件：整个函数用汇编写，ABI/栈/保存全自控。本目录 ncnn/src/layer/arm/ 下无 .S，说明 ncnn 偏好内联汇编就近写。

CUDA 侧对应物就是 PTX（可移植汇编）/ SASS（反汇编）——你 L3 CUDA 分级里「PTX/SASS 反汇编调优」那条，思路完全同构：手写/微调最接近硬件的那一层。

四、验证方法（落回你的工具链）

  1. 先 intrinsics 后 asm：用 §4/§6 的 intrinsics 写出来 → objdump -d 看编译器生成了什么（有没有 spill、顺序好不好）→ 把热块改成内联汇编微调。
  2. **objdump -d ./bin | grep -E 'fadd|fmla|sdot|vadd'**：确认出现 v 前缀 NEON 指令、且无 str/ldr 的 spill 痕迹。
  3. **perf stat -e instructions,cycles ./bin**：调度好了 = 同样工作量下 cycles 更少、IPC 更高。
  4. **perf annotate**：确认你手调的块真的以你写的顺序进了二进制（没被编译器挪走）。
  5. 查微架构手册：ARM《Cortex-A76 Software Optimization Guide》逐条列出每条指令的 latency/throughput——这是调度的「圣经」，比猜准。
