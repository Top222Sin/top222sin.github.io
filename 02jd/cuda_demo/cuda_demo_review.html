二、发现的问题

E1. ⚠️【较重要】cuda_l3_evt_fusion.md：声称 ORT 用”cuBLASLt 枚举 epilogue”落地 FusedMatMul，与所引源码备份不符

位置：cuda_l3_evt_fusion.md §二（第 61–87 行）与第 216 行；README 第 172/176 行。

声称内容：ORT 的 FusedMatMul = “复用 cuBLASLt，把融合塞进一个枚举 epilogue“，闭集为 CUBLASLT_EPILOGUE_DEFAULT | BIAS | RELU | BIAS_RELU | GELU | BIAS_GELU | DRELU（”7 种”）+ BIAS_POINTER。

事实（对备份 _ort_src/ 全量扫描）：

  • 整个备份零 cublasLt 引用（大小写不敏感全扫无命中）；
  • matmul.cc::ComputeDefault（FusedMatMul 实际执行路径，第 300–369 行）只用 cublasGemmHelper（beta=0），无 epilogue 枚举、无 BIAS_POINTER；
  • bias 的实际处理是 gemm.cc 的 β-trick（bias 预填 + cublasGemmHelper 带 beta）——这正是 cuda_l3_epilogue_fusion.md §三正确描述的内容；
  • 且 **”DRELU” 是 cuBLASLt 的真实标准枚举（CUBLASLT_EPILOGUE_DRELU=8，ReLU 梯度/反向）；现代 cuBLASLt 闭集已扩到 10+ 种（另含 DGELU/GELU_AUX/DRELU_BGRAD/BGRADA 等），原报告“DRELU 非标准”断言有误；”7 种”也过时）。

影响：读者会误以为 ORT 走 cuBLASLt epilogue 路线，与实际代码不符。建议：改为与备份源码一致的描述（bias 经 gemm β 巧法），或注明所描述的 ORT/cuBLASLt 版本（cuBLASLt epilogue 路径确实存在于部分 ORT 版本的 TunableOp 中——需作者确认版本后修正）。

E2. ⚠️ verify_neon_winobig_pack8.py：Windows GBK 控制台崩溃（12 项 PASS 但 exit≠0）

事实：脚本在结尾 print("... ✅/❌ ...") 处抛 UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'（Windows 默认 GBK 控制台），退出码 1——尽管 12 项检查全部 PASS。README 声称”python verify_neon_winobig_pack8.py → 全部 PASS”仅在 UTF-8 环境成立。
建议：结尾输出改 ASCII（[ALL PASS]/[FAIL]）或文档注明 $env:PYTHONIOENCODING='utf-8'。

E3. ⚠️ README”残差 1e-15”（F(3,3)）表述易误导

_solve_w33.py 的 ALS+Gauss-Newton 构造残差确为 1.69e-15，但 verify_neon_winobig_pack8.py 实际 2D 对拍 maxdiff≈1e-9（C++ 端用 12 位舍入常量）。md（cuda_l3_neon_winograd_big_pack8.md 第 182 行）已诚实披露”5b 的 ~1e-9 来自 C++ 端用 12 位舍入常量；全精度三元组可达 ~3e-15”，但 README 第 354/397/410 行的”残差 1e-15”未加限定，读者易理解为”对拍残差 1e-15”。建议统一口径。

E4. 📋 覆盖性提示（非错误）

  • 19 个 .cpp 未编译验证（沙箱无 nvcc/GPU）；”你会看到什么/预期”中的运行数字（9082.185693、DP launch=126/深度=6、overlap 100ms vs 765ms、K=3.004,a=3.004 等）本报告未经验证，需真机/编译器复核；
  • 19 篇 md 未逐篇精读（体量 + 环境限制），本报告覆盖了 README 全部数值、各篇的数值/硬件/API/引用类声明及 3 个 cpp 的确定性分析函数；
  • 建议后续在带 CUDA Toolkit + GPU 的环境执行 README”编译速查”的 16 组命令，并把真实输出回填 md。
