二、会写简单 kernel + 配置 launch bounds + 用 cudaMalloc / cudaMemcpy

对应笔记本：01CUDA基础学习.docx → L1 能跑（入门） → 2、会写简单 kernel，配置 launch bounds，用 cudaMalloc/cudaMemcpy
配套代码：cuda_l1_hello_kernel.cpp（saxpy + vsqr 两个 kernel + launch bounds + 完整 host 流程，注释即讲解）
双轨：本篇以 CUDA 为主，OpenCL 对照见第五节。

一、写一个”简单 kernel”到底在写什么

回忆 L1.1：**kernel 是一段”单条线程逻辑”**，你不写”如何并行”，只写”第 i 个线程算什么”。

本篇用 SAXPY 打头阵：z = a * x + y（blas 里最经典的 AXPY 带个系数 a）。

要点（和 L1.1 一脉相承）：

  • __global__：从 host 调用、在 device 执行，无返回值（void），结果写 z。
  • i 是这条线程的全局下标；所有线程跑同一份代码，各用各的 i、各取各的数据。
  • if (i < n) 边界保护：总线程数 = gridDim.x * blockDim.x 常比 n 大（grid 向上取整），越界线程必须跳过，否则写入越界显存。

一个 kernel 能”简单”，本质是：它只描述”一个元素的运算”。并行规模由 <<<grid, block>>> 决定，不在 kernel 里。

二、launch bounds：给编译器的”占用率提示”

2.1 语法

__launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor)：

  • 第 1 个参数：本 kernel 启动时每 block 最多多少线程。必须 ≥ 你实际启动的 blockDim.x，否则编译/运行出错。
  • 第 2 个参数（可选）：期望每个 SM 上至少同时驻留几个 block。

2.2 它到底改变了什么

这是面试/调优常问的点，一句话：它是给编译器的寄存器预算提示，间接决定 occupancy。

  • 你告诉编译器”256 线程 × 4 block 同时跑”→ 编译器算出每线程寄存器上限变小 → 倾向于少分配寄存器。
  • 寄存器用得少 → 能驻留更多 block/线程 → occupancy（SM 利用率）更高 → 更好地掩盖访存延迟。
  • 代价：寄存器不够时，编译器把变量”溢出”到 local memory（在 off-chip 显存上，慢）。所以第 2 个参数不是越小越好，是权衡。

2.3 怎么用

  • 只给第 1 个参数 是常态，告诉编译器 block 大小上界就够它优化寄存器了。
  • 加第 2 个参数 让编译器在”省寄存器换 occupancy”和”多寄存器换性能”之间权衡，适合你已通过 Nsight 发现 occupancy 偏低、且 kernel 寄存器压力大的场景。
  • 它不是必需语法——不写也能跑（如本篇的 vsqr）。它是”可选优化提示”，真要调 occupancy 时再配。
  • maxThreadsPerBlock 必须 ≥ 实际 blockDim.x：本例 blockSize=256，launch_bounds 写 256，正好贴合。

L2 你会用 Nsight Compute 看真实 occupancy 和寄存器用量，那时 launch_bounds 才有数据支撑。现在先记住”它是占用率提示”。

三、host 端的”五步数据流”：cudaMalloc / cudaMemcpy / cudaFree

一个标准 CUDA 程序的内存与执行流程：

3.1 cudaMalloc —— 在显存上开空间

  • 返回的是设备指针，host 端不能 *d_x 解引用（会段错误）。host 拿它只是”句柄”，用来传给 kernel / cudaMemcpy。
  • 失败返回 cudaErrorMemoryAllocation，生产环境要用错误检查（见代码里的 CUDA_CHECK 宏）。

3.2 cudaMemcpy —— 在 host 与 device 之间搬数据

  • 方向由最后一个参数决定：cudaMemcpyHostToDevice / cudaMemcpyDeviceToHost（还有 DeviceToDevice、HostToHost）。
  • 默认是同步的（stream 0）：调用返回时，这次拷贝已经完成。
  • 拷的是”主机虚拟地址 ↔ 设备地址”，runtime 按方向参数区分，两个指针类型不同（host 是普通指针，device 是 cudaMalloc 出来的）。

3.3 kernel 启动是异步的，但 D2H 会隐式等它

  • <<<grid, block>>> 启动 kernel 后，CPU 立即往下走，不会等 GPU 算完（异步）。
  • 因为 cudaMemcpy 在同 stream（默认 stream 0）上顺序执行，它在排队时会等前面提交的 kernel 完成——所以拷贝回结果前自动隐含了一次同步，**不用手动 cudaDeviceSynchronize()**。
  • 若你在 kernel 后立刻用 printf 打印 host 指针的结果而没拷贝，会读到旧数据/未初始化——别忘了 D2H 这步。

3.4 cudaFree —— 释放显存

  • 显存不会随函数返回自动回收，必须显式 cudaFree，否则显存泄漏。

3.5 两个固定套路

  • gridSize 向上取整确保覆盖全部 n 个元素（配合 kernel 内的 if (i < n)）。
  • blockSize 取 256 是常见起点（不超 1024 上限，且是 32 的整数倍，warp 对齐）。

四、错误检查：工业级写法

CUDA API 几乎都返回 cudaError_t。生产环境每个调用都应检查，否则错误会淹没在几百行后。

  • kernel 启动的错要用 cudaGetLastError() 查：因为 <<<>>> 是异步的，启动失败（参数非法、kernel 未注册、lauch bounds 不匹配）不会立刻在启动语句上抛错，必须紧接着查一次。
  • 本篇代码全程用 CUDA_CHECK 包裹，你照抄即可。

五、OpenCL 对照（双轨）

同一个 SAXPY，OpenCL 概念一一对应：

CUDA OpenCL
__global__ void saxpy(...) __kernel void saxpy(__global const float* x, ...)
__launch_bounds__(256,4) 无直接等价；靠 local_work_size 运行时决定，优化靠编译选项
cudaMalloc(&d, bytes) clCreateBuffer(ctx, CL_MEM_READ_WRITE, bytes, NULL, &err)
cudaMemcpy(d,h,bytes,H2D) clEnqueueWriteBuffer(q, d, CL_TRUE, 0, bytes, h, 0, NULL, NULL)
saxpy<<<grid,block>>>(args) clEnqueueNDRangeKernel(q, k, 0, &gws, &lws, 0, NULL, NULL)
cudaMemcpy(h,d,bytes,D2H) clEnqueueReadBuffer(q, d, CL_TRUE, 0, bytes, h, 0, NULL, NULL)
cudaFree(d) clReleaseMemObject(d)

差异点：

  1. OpenCL 没有 __launch_bounds__ 这种编译期占用率提示，occupancy 完全由你选的 local_work_size 决定。
  2. OpenCL 显式区分 cl_mem 对象与主机指针，读写都排队到 command queue；CUDA 的 cudaMemcpy 默认同步，用起来更像”普通 memcpy”。
  3. 底层 SIMT 模型（warp/wavefront）完全一致，差异只在 API 与运行时抽象层。

六、代码走读（cuda_l1_hello_kernel.cpp）

配套代码做了三件事，串起本篇全部知识点：

  1. saxpy_bounded：带 __launch_bounds__(256,4) 的 SAXPY，演示”配置 launch bounds”。
  2. vsqr：不带 launch_bounds 的向量平方，演示”简单 kernel 也能跑、launch_bounds 是可选提示”——复用同一套 host 流程。
  3. host main：cudaMalloc 开三块显存 → cudaMemcpy H2D 拷入 → <<<>>> 启动 → cudaMemcpy D2H 拷回 → 校验 → cudaFree。全程 CUDA_CHECK 包裹，启动后查 cudaGetLastError()。
