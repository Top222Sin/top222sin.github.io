前序：第 3 站把 CUTLASS epilogue（bias+激活+写回）与 ORT bias 巧法对照；本站把视角拉到整个算子——
一个 ONNX FusedMatMul 如何端到端映射到「一棵 epilogue 访客树 + 一组 MMA 形状」。

§零 这一站要回答的问题

第 3 站停留在「epilogue 内部怎么写 bias+激活」。本站问一个更大的问题：

给定一个 ONNX 融合算子 FusedMatMul（= GELU(α·A·B + bias)），工业界两条路线各自怎么把它落到 GPU kernel？

  • ORT 路线：把融合交给库封装的「输出算子」。本仓库备份的 _ort_src/ 实际走 cuBLAS cublasGemmHelper + bias β-trick（与 cuda_l3_epilogue_fusion.md §三一致）；ORT 其他 / 较新版本另有基于 cuBLASLt 枚举 epilogue 的 FusedMatMul 落地路线（见 §2.2，这是「库封装闭集」概念的真实来源）。
  • CUTLASS 路线：把融合写成一棵epilogue 访客树（EVT），MMA 形状显式写成一组 GemmShape。

两条路线最终都收敛到同一句话：

「MMA 计算段对所有 GEMM 系算子固定不变，差异全在『输出算子（epilogue）』这一个可替换点。」

区别只是：ORT 的输出算子（库内）是闭集枚举（cuBLASLt 给的有限几种，含真实标准的 DRELU 等），CUTLASS 的输出算子是开放可组合的树。

§一 ONNX FusedMatMul 是什么

com.microsoft.FusedMatMul（ORT contrib 算子）是图优化把 MatMul → Add(bias) → 激活 三段融合后的产物：

  • 输入：A[M,K]、B[K,N]、可选 Bias[N]（列广播）
  • 属性：alpha（默认 1.0）、transA、transB、activation（字符串："Gelu"/"Relu"/"FastGelu"/"None"）
  • 语义：Y = activation( alpha · A @ B + bias )

它就是 Transformer 里 Linear + Bias + Gelu 那一类算子的标准形态。

§二 ORT 怎么落地它：一个【枚举 epilogue】+ 不透明的 MMA

2.2 ORT 的另一条路线：cuBLASLt 的【枚举 epilogue】（其他 / 较新版本）

本节描述的是 ORT 其他 / 较新版本里基于 cuBLASLt 的 FusedMatMul 落地（如 TunableMatMul 的 cuBLASLt 后端），不是上面 §2.1 所引备份源码的实现（备份走 cublasGemmHelper + β-trick）。它作为「库封装闭集 epilogue」的代表，用来和 CUTLASS 的开放 EVT 树做概念对比。

而 epilogue 只能取固定枚举（示意子集，现代 cuBLASLt 已扩展到 10+ 种）：

  • DRELU（CUBLASLT_EPILOGUE_DRELU = 8）是真实的 cuBLASLt 标准枚举，含义是「对 matmul 输出求 ReLU 梯度」（用于反向传播，需额外 AUX 输入）；同族还有 DGELU、DRELU_BGRAD、GELU_AUX 等。「7 种」是较早版本的口径，现已过时。
  • activation="Gelu" + 有 bias ⇒ CUBLASLT_EPILOGUE_BIAS_GELU
  • 没有原生对应（如 FastGelu、Swish、任意自定义链）⇒ 枚举外 ⇒ 融合失败，ORT 必须把它退化成 MatMul + 独立激活 kernel。

2.3 关键限制：MMA 形状对 ORT 不透明

cublasLtMatmul 内部用 autotuner 自己挑 MMA tile / 调度 / 精度（TF32/FP16…）。
ORT 不指定、也拿不到这些 tile 几何——这是「库封装」的本质：省心但不可控。

这正是 ORT 路线与 CUTLASS 路线的分水岭：ORT 暴露「选哪个枚举 epilogue」；CUTLASS 暴露「tile 多大 + epilogue 树怎么长」。

§三 CUTLASS 怎么落地它：一组 GemmShape + 一棵 EVT 树

3.1 MMA 形状显式写成三级 GemmShape

三级形状 + kStages 全部用户指定——你精确控制占用率、shared memory、pipeline 深度。
（详见第 2 站 cuda_l2_cutlass_gemm.* 对 tiling/双缓冲/pipeline 的拆解。）

3.2 epilogue 是一棵【访客树】（EVT，Epilogue Visitor Tree）

CUTLASS 3.x 的 DefaultEpilogue 持有一个 ThreadEpilogueOp（即 EVT 树），逐元素调用
（include/cutlass/epilogue/collective/default_epilogue.hpp:63,239,248）：

EVT 的节点族（include/cutlass/epilogue/collective/sm80_visitor.hpp 一系的 Sm80EVT/Sm90EVT）：

节点（示意名） 仿自 作用
VisitorAuxLoad 叶子 从某张量取数（bias 列广播 / C 逐元素 / side-output）
VisitorCompute 一元/二元 对累加器做激活（gelu/relu）或二元组合（plus/multiplies）
VisitorAuxStore 根 把结果写回 D（或某个 side-output）
VisitorReduction 特殊 对 tile 内做行/列归约（softmax 类）

树的后序求值：根=StoreD，累加器 accum 自顶向下贯穿，二元 Compute 的左操作数永远是 accum，右操作数是孩子节点。

3.3 开放性：换一个节点即可，MMA 一行不动

要改 GELU→RELU，或加一个 Swish，只换/加一个 VisitorCompute 节点，三级 GemmShape 与 pipeline 完全不动。
这是「模板元编程 + 编译期树」带来的可组合性。

维度 ORT FusedMatMul CUTLASS Gemm + EVT
算子落点 其他版本：cublasLtMatmul + 枚举 epilogue；本备份：cublasGemmHelper + β-trick Gemm<GemmShape…, kStages, EVT>
epilogue 表示 从 {DEFAULT,BIAS,RELU,BIAS_RELU,GELU,BIAS_GELU,DRELU} 选 1 用户任意组合的访客树
bias 处理 CUBLASLT_MATMUL_DESC_BIAS_POINTER（列广播） VisitorAuxLoad<bias> 节点
MMA 形状 cuBLASLt 内部 autotuner 选，不透明 显式 GemmShape<BM,BN,BK>/<WM,WN,WK>/<IM,IN,IK> + kStages
新激活（Swish） 枚举外 → ❌ 退化成独立 kernel ✅ 加一个 VisitorCompute 节点

可控性 低（黑盒库） 高（tile/pipeline/epilogue 全暴露）
易用性 高（一行属性） 低（要写模板/kernel）

§五 开放 vs 闭集：Swish 测试（代码已验证思路）

  • CUTLASS：run_evt(Accum, M, N, &bias, h_swish) —— 把激活函数换成 swish(x)=x/(1+e^-x) 即可，MMA 形状一行未动，D 正常产出。
  • ORT：ort_map_epi(true,"Swish") 返回 EPI_UNSUPPORTED —— cuBLASLt 没有 Swish 的原生 epilogue，
    融合失败，必须退化为 [MatMul] + [独立 Swish kernel] 两个 kernel，多一次全局显存往返。

这就是「库封装」与「可组合模板」的根本权衡：库的甜区在它支持的那几个 fusion；树的优势在它什么都能拼。

§六 代码走读（cuda_l3_evt_fusion.cpp）

  1. run_evt(...) —— 用纯 C++ 复刻 CUTLASS EVT 的后序求值：
    StoreD( UnaryOp(act, BinaryOp(plus, AuxLoad(BIAS))) )。

    • AuxLoad：仿 VisitorAuxLoad，BIAS 走列广播 data[n]，C_TENSOR 走逐元素。
    • UnaryOp/BinaryOp：仿 VisitorCompute，二元节点左操作数恒为 accum（MMA 累加器）。
    • StoreD：仿 VisitorAuxStore，写回 D[m*N+n]。
    • 顶部循环把 Accum[m*N+n]（已含 α 的 MMA 输出）作为 accum 灌入树根。

  2. ort_map_epi(has_bias, activation) —— 复刻「ONNX 激活名 → cuBLASLt 枚举 epilogue」的闭集映射；闭集外返回 EPI_UNSUPPORTED。

  3. ort_fused_matmul(...) —— G = α·A·B（MMA 由「cuBLASLt 内部」选形状），再套用枚举 epilogue；返回 false 表示退化。

  4. main() 对拍：D(EVT)、D(ORT)、D(ref) 三路比对，max|Δ|<1e-4 判 PASS；并演示 Swish 的开放/闭集差异。

运行预期：[EVT] PASS、[ORT] PASS，并打印 ORT 融合成功、Swish 在 ORT 侧退化的对照结论。

§七 OpenCL 对照

  • OpenCL 没有 cuBLASLt 那种「枚举 epilogue」原语，也没有 CUTLASS 的编译期访客树。
  • 融合 GEMM+偏置+激活在 OpenCL 里通常要么手写一个 kernel（在 kernel 内 acc = alpha*dot + bias; out = gelu(acc);），
    要么拆成多个 kernel（clBLAS gemm + 自定义 activ）——前者接近 CUTLASS 的「可控」但需自己写 tiling，
    后者接近 ORT 退化路径的「多一次往返」。
  • 结论一致：能否「单 kernel 融合任意算子」取决于你的抽象是否开放可组合，而不取决于具体是哪家的后端。

§八 自检

  • 能说出 FusedMatMul 的语义 Y = activation(α·A@B + bias) 及其三个输入/属性。
  • 能在 fused_matmul.cc 里指出它复用了 MatMul<T> 内核（:19,27-30）。
  • 能说明 ORT 两条 FusedMatMul 落地路线（本备份 cublasGemmHelper + β-trick；其他版本 cublasLtMatmul + 枚举 epilogue），并背出 cuBLASLt epilogue 枚举（含真实标准的 DRELU，现代已 10+ 种）与 BIAS_POINTER 的作用。
  • 能解释为什么 ORT 的 MMA 形状是「不透明」的（cuBLASLt autotuner）。
  • 能画出 CUTLASS 的 EVT 树：StoreD ← gelu ← plus ← [accum, AuxLoad(bias)]。
  • 能解释 GemmShape<BM,BN,BK>/<WM,WN,WK>/<IM,IN,IK> + kStages 是 MMA 形状的「显式」表达。
  • 能用「Swish」例子说明开放（CUTLASS 加节点）vs 闭集（ORT 退化）的差异。
