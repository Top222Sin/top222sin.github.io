工业级 CUDA EP 实战：读 onnxruntime 的 kernel 分块与内存优化

源码蓝本：microsoft/onnxruntime（main 分支，2026-08 拉取）
配套代码：cuda_l3_ort_industrial.cpp（把工业 kernel 拆成可编译、可 CPU 校验的教材版）
前文衔接：L2.1 内存层次/合并/bank conflict/双缓冲 → L2.2 warp/分支发散/occupancy/寄存器压力 → L2.3 profiling/compute-bound vs memory-bound → L2.4 手写 reduction + tiling → 本节「工业级怎么落地」

一、为什么读 onnxruntime，而不是自己 yy

onnxruntime 的 CUDA EP 是生产级推理引擎，它的每个 kernel 都经历过：正确性、跨架构（sm_50→sm_90）、混合精度（fp32/fp16/bf16）、占用率、与 cuBLAS/cuDNN 的取舍。读它等于直接看「一个被几十亿次调用检验过的 kernel 长什么样」。我们对着真实源码（不是二手博客）提炼出 6 条可迁移模式，逐条都能回扣到 L2.1–L2.4。

拉取的 5 个关键文件：

  • tensor/transpose_impl.cu —— 分块转置 + int4 向量化 + 自适应 grid/block
  • math/softmax_impl.cu + math/softmax_warpwise_impl.cuh —— warp 级归约 + 寄存器回退
  • nn/layer_norm_impl.cu —— 跨 warp 归约 + grid-stride + Welford 在线算法
  • math/gemm.cc —— GEMM 直接交给 cuBLAS/cuBLASLt（库做极致 tiling）

二、六条工业级模式（附真实源码）

模式 1：分块转置 + [TILE][TILE+1] padding

源码：transpose_impl.cu:10-46（Transpose3DKernel）

  • 为什么 +1：L2.1 讲过 bank conflict。tile[T][T+1] 里元素 [r][c] 落在 bank((r*(T+1)+c)%32)。T=32 时 (r*33+c)%32 = (r+c)%32，写阶段同 warp 的线程访问 tile[tx][ty+i]，bank=(tx+ty+i)%32，固定 i 时各 lane 互不相同 → 0 冲突（见 cuda_l3_ort_industrial.cpp 的 analyze_ort_patterns() 推导，已用 Python 验证：无 pad 时 32 个线程全部落同一 bank → 32 路冲突的最差情况；加 +1 后降为 0）。
  • 和朴素版的区别不是”少读字节”，而是”合并”：朴素 out[x*m+y]=in[y*n+x] 写输出是跨步的（不合并）；tiling 让读、写都合并，事务数大降。这回扣 L2.4 的洞见——tiling 不改变 AI（字节数不变），但砍掉冗余事务/访存延迟。

模式 2：向量化访存（int4 一次搬 16 字节）

源码：transpose_impl.cu:121-126

  • 把连续 4 个 int（或 16 个 int8）打包成 int4 一次读写，提升有效带宽利用率、增加 ILP（指令级并行），减少取指/事务开销。这是工业 kernel “榨干带宽” 的标配，呼应 L2.1 的”合并”和 L2.3 的”memory-bound 先看带宽”。

模式 3：warp 级归约靠 __shfl_xor，不碰 shared memory

源码：softmax_warpwise_impl.cuh:45-56（warp_reduce）、:126、:141

  • 这正是我们 L2.4 reduce_warp_shuffle 的工业原型：归约在寄存器内用 shuffle（蝶形 XOR） 完成，**不需要 shared memory、不需要 __syncthreads()**，延迟最低。
  • onnxruntime 把 max、sum 两次都用 warp_reduce 做完，再写回。还做了个细节优化：倒数只算一次（acc_t invsum = 1.0f/sum;），把除法换成乘法。

模式 4：寄存器压力 → 回退到 shared memory

源码：softmax_warpwise_impl.cuh:165-233（softmax_warp_forward_resource_efficient）

注释原话：

“softmax_warp_forward uses register to store data in fp32 even when data is fp16, which will cause register resource oversubscription when data is large, and will lead to low CUDA warp occupancy and thus a poor kernel performance.”

  • 元素数小（<=128）时用纯寄存器（一个 warp 同时算 2 行，WARP_BATCH=2）。
  • 元素数大时寄存器装不下 → 改为把原始 dtype（如 half）缓存进 extern __shared__，需要时再 cast 成 fp32 计算（”用重算换寄存器”）。
  • **这正是 L2.2 讲的”寄存器压力”**：每线程寄存器太多 → spill 到 local memory（本质是 global）→ 占用率下降。onnxruntime 用”降寄存器占用、保 occupancy”来对冲，是生产代码的典型权衡。

模式 5：跨 warp 归约 + grid-stride（layer norm 的 Welford）

源码：layer_norm_impl.cu:136-179（归约）、:345（for (i1=blockIdx.y; i1<n1; i1+=gridDim.y)）

  • 这是比 L2.4 reduce_halving（交错寻址、stride=32 还冲突）更工业的写法：warp 内 shfl（无冲突），warp 间用 ubuf/ibuf 显式 shared 合并，且 HostApplyLayerNorm 会**按 n2 与设备能力自适应 threads_y**（round_up_power_of_2 + 受 maxThreadsPerBlock 约束），在”并行行数”和”单块占用”之间选平衡——这就是 L2.2 occupancy 的落地。
  • 外层 i1 += gridDim.y 是 grid-stride 循环：一个 block 负责多行，配合 host 端算出的 parallel_rows，让 SM 始终有活干。

模式 6：GEMM 不手写 tiling，交给库（抽象边界）

源码：gemm.cc:78-79、gemm.cc:157

  • 重要的工程判断：矩阵乘这种”极致手活”不自己写，而是调 cuBLAS/cuBLASLt（它内部有 workspace、算法启发式、Tensor Core 路径、针对不同 M/N/K 的专门 kernel）。自己只做：shape 解析、broadcast bias、绑定到正确的 stream。
  • 还藏着两个坑处理：① 列主序陷阱——CUDA 的 GEMM 是列主序，所以 Y(N,M)=α·op(W)·op(X)，和 L1.3 学的 cublasSgemm 一模一样；② bias broadcast 用 cublasGemmHelper(..., GetConstOnes, ...) 这种”用一次小 GEMM 代替循环”的巧法。

四、与 L2.1–L2.3 的串联（一张表）

我们学过的点 onnxruntime 怎么用 源码位置

L2.1 合并访问 读写都合并；int4 向量化提带宽 transpose_impl.cu:121

L2.4 reduce_halving→跨 warp shfl_down + shared buffer 合并 layer_norm_impl.cu:136

五、工业级工程的”额外清单”（看源码顺手学到的）

  1. 小元数据按值传，避免额外拷贝：cuda_utils.h 的 TArray<T,capacity> 把 shape 等小数组直接 memcpy 进 kernel 参数（寄存器/常量区），省一次 cudaMemcpy。
  2. 永远绑定 stream，绝不用默认流：cudaMemcpyAsync(out, b, ..., Stream(ctx))（gemm.cc:140）。默认流会串行化整个 GPU，是性能 bug 高发区（L2.3 nsys 时间线的”空隙”常源于此）。
  3. 模板特化实例化：SPECIALIZED_WRAPWISE_SOFTMAX_IMPL(float,float,float) 等一组宏，把 fp32/fp16/bf16/double 显式实例化，避免全量模板膨胀、控制编译时间。
  4. GetDeviceProp() 自适应：grid/block 上限（maxGridSize/maxThreadsPerBlock/warpSize）都查设备属性，保证跨 GPU 可移植。
  5. 算法选择与 tuning：TunableGemm 在若干候选算法里运行时择优，而不是写死一个。
