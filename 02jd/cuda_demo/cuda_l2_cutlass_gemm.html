CUTLASS GEMM 分块 vs onnxruntime 工业模式

看 CUTLASS 如何把「tiling + 双缓冲 + pipeline + Tensor Core」封装成可复用模板

配套：cuda_l2_cutlass_gemm.cpp（缩小版 CUTLASS 参考 kernel + CPU 对拍 + 确定性量化）、
images/fig9_cutlass_gemm.svg + cuda_l2_cutlass_gemm_diagrams.html（四联图）。
真实源码（NVIDIA/cutlass main 分支，2026-08 拉取，备份于 cuda_demo/_cutlass_src/）：
include/cutlass/gemm/threadblock/mma_multistage.h、.../kernel/gemm.h、.../device/gemm.h。

0. 为什么读 CUTLASS（承上启下）

上一节我们读 onnxruntime CUDA EP，发现它对 GEMM 根本不手写分块，而是直接交给
cuBLASLt / TunableGemm（gemm.cc:79,157）。这恰恰指向真正”把分块+双缓冲+pipeline+
Tensor Core 写成极致模板”的工程——CUTLASS。CUTLASS 既是独立库，也是 cuBLAS/cuBLASLt
背后的手写 GEMM 实现基础。

所以本节路线：把上一节看的 transpose / softmax / layernorm 三种”工业手写 kernel”套路，
对照 CUTLASS 的 GEMM 模板，看清”手写高手”是怎么把这些套路抽象成可复用模板的。

1. CUTLASS 的四件套封装总览

CUTLASS 把四个关注点拆成模板参数 + 组件类，互不耦合：

关注点 CUTLASS 落点 真实源码
tiling（分块） ThreadblockShape / WarpShape / InstructionShape 三模板 + ThreadblockSwizzle device/gemm.h:150-167、kernel/gemm.h:206-227
双缓冲 int kStages 模板 → 共享内存多份 K 切片环形缓冲；寄存器级 warp_loaded_frag_[2] mma_multistage.h:58-91,178-184,249-285
pipeline cp.async + cp_async_fence() + cp_async_wait<>() + prologue() 灌水 mma_multistage.h:311-316,434,489,362-481

公共 API（device/gemm.h:150-167）就是把它们”装进一个类”：

一句话：onnxruntime 的 tile[32][33]、__shfl_xor、grid-stride 是单点技巧；
CUTLASS 把它们提升为模板参数 + 组件接口，于是”换精度 / 换 tile 形状 / 换 2 缓冲还是 3 缓冲 /
换 SIMT 还是 Tensor Core”只改模板实参，不动 kernel 主体。

2. tiling —— 三级 GemmShape + ThreadblockSwizzle

2.1 三级 tile 形状（对照 ORT transpose 的”一个固定 tile”）

onnxruntime 的转置只写死一个 tile[32][33]（transpose_impl.cu:18）。CUTLASS 把”tile”拆成
三层，每层独立模板化：

  • ThreadblockShape（CTA 级 tile）：一个 block 负责 M×N 输出块、每步搬 K 切片，如 <128,128,8>。
  • WarpShape（warp 级 tile）：一个 warp 在 CTA 内再分 M×N，如 <64,64,8>。
  • InstructionShape（指令级 tile）：一次 Tensor Core 的形状，如 <16,8,8>（即 mma.sync.m16n8k8）。

在 kernel 里直接用（kernel/gemm.h:220-227）：

Mma::Shape::kM/kN/kK 就是 ThreadblockShape 的三个维度——tiling 就是模板常量，
CTA 网格 grid_tiled_shape 自动按它切分全局问题。

2.2 ThreadblockSwizzle（对照 L2.1 合并访问）

onnxruntime transpose 要手工保证合并；CUTLASS 用 ThreadblockSwizzle 在 运行时重排
CTA 的执行顺序，让相邻 CTA 访问相邻显存，天然合并（kernel/gemm.h:206-209）：

回扣 L2.1：swizzle 本质就是”用地址重排换合并访问”，和 ORT 把 tile[32][33] 的 +1
都是为了消灭 bank/合并冲突——只是 CUTLASS 把它做成了可参数化的通用组件。

2.3 确定性量化（见 analyze_cutlass_tiling()）

典型 FP16 配置 TB<128,128,8> / W<64,64,8> / I<16,8,8> / kStages=3：

  • 每 CTA warps = (128/64)×(128/64) = 4（128 线程）；
  • 每 warp MMA 数 (64/16)×(64/8)×(8/8) = 4×8×1 = 32；每 K 步 CTA 总 MMA 32×4 = 128。

3.1 共享内存多份 K 切片（环形缓冲）

3.2 寄存器级双缓冲（让”取下一 warp-tile”与”算当前”重叠）

除了共享内存的多份，CUTLASE 还在寄存器上开两份 fragment（mma_multistage.h:178-184）：

主循环里用 (warp_mma_k + 1) % 2 交替索引，实现”提前取下一 warp-tile 进寄存器，
当前 warp-tile 在跑 MMA”（:505-607）：

对照 ORT softmax（softmax_warpwise_impl.cuh:45）用 __shfl_xor 在寄存器间归约、
ORT layernorm 把跨 warp 的部分和放共享内存——两者的共同目标都是”省一次 shared 往返”。
CUTLASS 的 warp_loaded_frag_[2] 是同一思想的模板化极致：用寄存器双缓冲彻底消除
“取数→计算”的依赖停顿。

3.3 确定性量化（见 analyze_cutlass_tiling()）

单 K 步：全局抓取 2·TB_M·TB_K + 2·TB_K·TB_N 字节写进 shared 后，被 warpsPerCTA 个 warp
在各自 W_K/I_K 次 MMA 中复用 → 共享复用 ≈ TB_M·TB_N 元素/步。这正是 L2.4 说的
“每个全局元素只取 1 次、被 tile² 线程复用”，只是 CUTLASS 把它写成模板自动展开。

4. pipeline —— cp.async + 围栏 + prologue 灌水

这是 CUTLASS 和 ORT 手写 kernel 最大的结构差异：ORT 用普通 __syncthreads + 手动循环，
CUTLASS 用 cp.async（异步拷贝指令）+ 屏障 把”生产者（HBM→shared）”和”消费者（MMA）”
解耦。

4.1 生产者：cp.async（HBM → shared，copy engine 异步做）

注意 iterator_A.valid() 做边界谓词——越界 K 片用 zfill/predicate 处理（对照 L2.2 分支发散：
predicate 是”每线程自己判断”，不引发 warp 发散）。

4.3 prologue()：预取 kStages-1 个 stage 灌满流水线（bootstrap）

不等全部搬完再算——先灌满 kStages-1 份，主循环一边算一边补（:362-481）：

对照 ORT layernorm（layer_norm_impl.cu:136）的”跨 warp 归约 + grid-stride 循环”：
二者都在管理”生产者/消费者”重叠，但 ORT 是手写 while + 原子，CUTLASS 是
kStages 模板 + 显式 pipe state + cp.async 指令——把”重叠”做成可验证、可穷举调优的模板。

4.4 主循环三段交错（mac_loop_iter，:505-607）

对每个 warp-tile：

  1. 提前取下一 warp-tile 的 A/B 碎片（shared→reg，双缓冲索引）；
  2. 执行当前 warp-tile 的 MMA（warp_mma_(...)）；
  3. 发出下一 stage 的 cp.async（生产者补货）。
    三组动作交错，使 Tensor Core 几乎不被 HBM 延迟饿着。

5.1 Operator 是把”算法”抽象出来的组件

MmaMultistage 持有一个 warp 级 MMA 算子（mma_multistage.h:122-123,194）：

调它就是在发 Tensor Core 指令（:541-546）：

Operator 底层（warp 级 MmaTensorOp / arch::Mma<GemmShape<16,8,8>,...>）最终发出
mma.sync.aligned.m16n8k8.row.col.f16.f16.f16.f32 这类 PTX——这正是
InstructionShape<16,8,8> 的来历。

5.2 对照 ORT GEMM 的”交库”决策

onnxruntime 的 gemm.cc:79,157 直接调 cuBLASLt / TunableGemm，不手写这一层。
这正是工程边界判断的范例：

  • 极致手活（分块 + 双缓冲 + pipeline + Tensor Core）→ 交给 CUTLASS / cuBLASLt；
  • shape / broadcast / bias / stream / 类型胶水 → ORT 自己写。

CUTLASS 把”Tensor Core 怎么用”封装成 Operator 组件，于是 ORT 想换 SIMT/TensorOp、
换精度，只改模板，不碰 MMA 指令。这就是”可复用模板”相对于 ORT 单点 kernel 的根本优势。

6. 与 onnxruntime 三件套的一一对照表

onnxruntime 模式（上一节） CUTLASS 对应封装 升级点
transpose tile[32][33] +1 破 bank conflict ThreadblockShape 模板 + ThreadblockSwizzle 固定 tile → 可参数化三级 tile + 自动 swizzle
softmax __shfl_xor warp 归约（省 shared） Operator 组件（SIMT / TensorOp 可换） 单点技巧 → 组件接口，可替换算法
layernorm 跨 warp 归约 + grid-stride kStages + prologue/pipeline 管 生产者/消费者 手写 while+原子 → 模板化 pipe state + cp.async
GEMM 直接交 cuBLASLt（gemm.cc） CUTLASS 即其底层手写模板 工程边界：自己只写胶水

7. 工程上怎么”复用” CUTLASS（给自己的边界判断）

  1. 别重写 GEMM：直接用 cutlass::gemm::device::Gemm<ThreadblockShape, WarpShape, InstructionShape, kStages, ...>，按精度/形状选模板实参即可（device/gemm.h）。
  2. 自定义 epilogue：CUTLASS 把”bias + 激活 + 写回”做成 Epilogue 组件
    （kernel/gemm.h:332 epilogue(output_op, iterator_D, accumulators, iterator_C)）——
    仿 ORT 的 bias broadcast 巧法，可挂自己的 EpilogueOp。
  3. 自定义算子复用 tiling/pipeline：想写非 GEMM 的高性能 kernel（如 conv、softmax、
    layer_norm），直接套 MmaMultistage 的”双缓冲 + cp.async pipeline”骨架——这正是
    CUTLASS 3.x / CuTe 的方向：用同一套 pipeline 原语描述任意算子。
  4. 调优思路：kStages、tile 形状、swizzle 都是穷举调优维度；这正是 NVIDIA
    CUTLASS Profiler / 启发式库做的事。

8. 自检（看 cuda_l2_cutlass_gemm.cpp 输出）

  1. tiny_gemm_ref_cpu(A, I) 结果应等于 A 本身（单位阵）✅ 一致性 PASS。
  2. analyze_cutlass_tiling() 打印：warps=4 (threads=128)、
    每 warp MMA=32、kStages=3、S=256 全局流量下降 171×、
    AI≈0.167 FLOP/Byte（与 L2.3/L2.4 一致）。
  3. tiny_wmma_gemm<64,64,32,2>（WMMA Tensor Core + 双缓冲 + prologue/mainloop 骨架）
    真机跑 run_gpu_checks()：max|GPU-CPU| < 1e-2（FP16 精度）。
  4. 能在 device/gemm.h 找到 ThreadblockShape/WarpShape/InstructionShape/kStages 四个模板参数，
    在 mma_multistage.h 找到 cp_async / cp_async_fence / cp_async_wait /
    prologue / warp_loaded_frag_[2] 五处源码。

9. 与学习路线的串联

  • L2.1 合并/bank conflict：ThreadblockSwizzle 是合并的模板化；+1 padding 思想被吸收进
    shared 内存 ThreadblockSwizzle 与 fragment 布局。
  • L2.2 warp / 分支发散：cp.async 的 valid() 谓词是”每线程独立判断”，不引发 warp 发散；
    Operator 组件让 SIMT/TensorOp 可换。
  • L2.3 compute/memory-bound：双缓冲 + pipeline 隐藏 HBM 延迟，让 compute-bound 的
    Tensor Core 吃满带宽（Roofline 上移向算力屋顶）。
  • L2.4 共享内存归约 / 分块 tiling：CUTLASS 的 kStages 环形缓冲 + warp_loaded_frag_[2]
    是你手写 matmul_tiled / reduce_warp_shuffle 的工业升级版。
  • 上节 ORT：CUTLASS 是 ORT “交库”背后那层手写模板；二者对照，看清”单点技巧 → 可复用模板”。
