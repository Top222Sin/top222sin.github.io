L3.3　cooperative groups + dynamic parallelism + PTX/SASS 反汇编调优

配套代码：cuda_l3_cg_dp_ptx.cpp（纯 C++ 可跑）　图示：images/fig14_l3_cg_dp_ptx.svg / cuda_l3_cg_dp_ptx_diagrams.html
编译运行：g++ -O3 -std=c++17 cuda_l3_cg_dp_ptx.cpp -o cg && ./cg → 预期 [verify_on_cpu] PASS
真机：nvcc -O3 -std=c++17 -arch=sm_80 -rdc=true cuda_l3_cg_dp_ptx.cpp -lcudadevrt -o cg_gpu

这三个主题看似分散，其实是同一件事的三个层面：把并行结构表达得更贴近硬件，让 SM 少空转。

  • cooperative groups：把「跨 block 协作」变成一等公民（一次栅栏替代一次 kernel launch）；
  • dynamic parallelism：把「工作量随数据自适应」的决策留在设备端（不回 host）；
  • PTX/SASS 反汇编：打开黑盒，看编译器到底发了什么指令，验证前面所有优化是否真的落地。

§0　承上启下：L3 的三站怎么串

站 关注点 一句话
L3.1 fusion + cp.async + pipeline 减少「搬多少」与「搬时干等」
L3.2 Tensor Core + 混合精度 让「算」这一步更密更快
L3.3（本站） CG / DP / 反汇编 调度结构（跨 block 协作、自适应并行）+ 验收手段（看 SASS）

前两站教你「写出高性能 kernel」，本站教你「组织多 kernel/多 block 的协作」并「用反汇编验收」——是把整条链闭合的最后一环。

§1　cooperative groups：从 __syncthreads() 到 grid.sync()

痛点：CUDA 9 之前，同步只能到 block 内（__syncthreads()）。跨 block 想同步，唯一办法是结束当前 kernel、host 再 launch 下一个 —— 每次都付出 launch 开销 + 全局状态失效。

cooperative groups 把「一组协作线程」抽象成可同步的 group，粒度从 sub-warp 一直到整个 grid、甚至多 GPU：

通用接口：g.sync() / g.size() / g.thread_rank()；tile 还有 .shfl_down() / .ballot() / .any()（编译期尺寸→快）。

关键：grid.sync() 把「两趟 kernel」压成「一趟 + 一次栅栏」

经典两-kernel 归约：kernel A 出 partial[] → 结束 → host launch kernel B 归约 partial[]。
cooperative 版：一个 persistent kernel 内 phase1 → grid.sync() → phase2。

启动方式必须换（不能用 <<<>>>）：

⚠️ 硬约束：grid.sync() 要求所有 block 同时驻留（否则死锁）。所以 grid 大小不能随便填，要用 occupancy API 估「一个 SM 能放几个 block」再乘 SM 数。设备需支持 cooperativeLaunch 属性。

收益（代码 demo_cooperative_groups() 量化）：省 1 次 kernel launch、省 1 组 partial[] 全局往返。对迭代型算法（Jacobi、共轭梯度、persistent RNN）收益放大——本来每次迭代一趟 kernel，现在整个迭代循环装进一个 kernel，每轮一次 grid.sync()。

与 L2.4 闭环：block 内 shared 归约是「近」协作，grid.sync() 是它的「跨 block」放大版——同一套树形归约思想，作用域从 block 抬到 grid。

权威依据：CUDA C++ Programming Guide《Device-Callable APIs》——grid_group grid = this_grid(); grid.sync(); 与 cudaLaunchCooperativeKernel(...)、cudaOccupancyMaxActiveBlocksPerMultiprocessor(...) 的协作启动范式（docs.nvidia.com/cuda/…/05-appendices/device-callable-apis.html）。

§2　dynamic parallelism：kernel 内 launch kernel

动机：有些算法的工作量随数据变化——自适应网格细分（AMR）、树遍历、递归排序、图搜索。传统写法要「kernel 跑一趟 → 回 host 看结果 → 决定下一步 launch 多少」，来回往返。dynamic parallelism（DP） 让父 kernel 在设备端直接 launch 子 kernel，决策不回 host。

编译：需 relocatable device code + 链接设备运行库：

⚠️ CDP2（CUDA 12）的重大变化

  • 设备端 cudaDeviceSynchronize() 已被移除（CUDA 11.6 起弃用、12 移除）。父 kernel 不能在中途等子 kernel 完成。
  • 依赖关系改用流语义表达：
    • cudaStreamFireAndForget：并发派发，父不等（本例用它，靠 atomicAdd 汇总）；
    • cudaStreamTailLaunch：父 kernel 全部结束后再跑子 kernel（表达「先父后子」的顺序依赖）。

收益（代码 demo_dynamic_parallelism() 量化）：N=65536、cutoff=1024 → 二叉自适应树 child launch=126 次、最大深度=6，结果与朴素求和一致（PASS）。真实价值不在「求和」（那用 CG 更好），而在工作量高度不均的场景：均匀区域早停、复杂区域递归细分，省去大量「回 host 决策」的往返。

代价：设备端 launch 也有开销（每次 launch 要建 grid），太细的递归会被 launch 开销吃掉收益 → cutoff 要调大到「叶子工作量 ≫ launch 开销」。

§3　PTX vs SASS：两层 ISA

PTX SASS
定位 虚拟 ISA（跨架构、稳定，类比 GPU 的 LLVM IR） 原生 ISA（每架构一套，SM 真正执行的）
谁生成 nvcc 前端 ptxas / 驱动 JIT
看到它 nvcc -ptx nvdisasm / cuobjdump --dump-sass
助记符 ld.global st.shared fma.rn.f32 cp.async mma.sync shfl.sync cvt LDG STS FFMA LDGSTS HMMA SHFL F2F
宽度 无固定宽度 Volta+ 固定 16 字节/指令

一条 PTX → 一/多条 SASS（不保证一一对应，ptxas 会调度/优化）。经验法则：用 PTX 理解语义（可移植），用 SASS 判断真实代价（贴硬件）。

从 C → PTX → SASS 的映射（以 y = a*x + y 为例）：

抓主干即可：访存是 LD*/ST*，算术是 F*（浮点）/I*（整数），控制流是 BRA/BSSY/BSYNC。

权威依据：CUDA Binary Utilities（docs.nvidia.com/cuda/…/cuda-binary-utilities）给出 nvdisasm -cfg 控制流图与寄存器 liveness 输出示例，及 FFMA.FTZ / STG.E.SYS / @!P0 BRA 等真实 SASS 片段；SASS 指令代际表（Volta 引入 HMMA、Ampere 引入 LDGSTS/LDGDEPBAR）见社区整理的 Instruction Set 历史。

§5　SASS 分诊：从指令读性能信号（代码 analyze_sass()）

demo_sass_triage() 内嵌一段示意 SASS 并解析，给出体检报告。核心信号：

指令 含义 判读
LDL / STL local memory 读/写 寄存器溢出（坏）→ 降 occupancy；减寄存器 / 加 __launch_bounds__ / 拆 kernel
LDGSTS Ampere cp.async（global→shared 直搬） ✅ L3.1 异步拷贝已生效
HMMA / IMMA Tensor Core 矩阵乘（fp16/int8） ✅ L3.2 TC 路径已走
FFMA 融合乘加 好；若见成对 FMUL+FADD = 未融合，检查 --fmad=true/精度标志
LDG.E.128 128-bit 向量化全局 load ✅ 合并访问良好（coalescing）
@P / @!P 谓词化执行 发散被压平（好）——两条路径都执行但按 predicate 写回
BRA 真分支跳转 潜在 warp 发散（回看 L2.2）；分支两侧工作量差异大时代价高

本站示例 SASS 的分诊结论（代码实测）：LDGSTS×1（cp.async 命中）、HMMA×1（TC 命中）、LDG.E.128×1（向量访存）、FFMA×1 但有 1 组 FMUL+FADD 未融合、STL×1 LDL×1（有溢出，先修）、BRA×1（真分支，潜在发散）+ 谓词化 @P×2。

优先级：寄存器溢出（LDL/STL） 和 真分支（BRA） 是最先要消灭的两类；LDGSTS/HMMA/LDG.128 出现则说明高级特性已启用。

与 L2.2 闭环：@P 谓词化就是编译器把「短小 if」压平成两路都算、按掩码写回——正是 warp 分支发散的硬件级应对；SASS 里 BRA 多而 @P 少，说明发散没被压平，回去用 __ballot_sync/重排数据消除。

§6　真实源码 / 文档锚点

  • cooperative groups：CUDA C++ Programming Guide《Device-Callable APIs and Intrinsics》—— this_grid()/grid.sync()、cudaLaunchCooperativeKernel、cudaOccupancyMaxActiveBlocksPerMultiprocessor 协作启动约束（“all thread blocks are simultaneously resident”）。
  • dynamic parallelism：CUDA C++ Programming Guide《CUDA Dynamic Parallelism》—— -rdc=true -lcudadevrt、CDP2 移除设备端 cudaDeviceSynchronize()、cudaStreamTailLaunch/cudaStreamFireAndForget 流语义。
  • PTX/SASS：CUDA Binary Utilities —— nvdisasm -g/-cfg、寄存器 liveness、FFMA.FTZ/STG.E.SYS/@!P0 BRA 片段；SASS 代际（Volta HMMA、Ampere LDGSTS/LDGDEPBAR、Turing LDSM）。

§8　编译与运行

一句话收束：grid.sync() 让跨 block 协作不再靠 kernel 边界；dynamic parallelism 让自适应工作量不再回 host 决策；PTX/SASS 反汇编让前两站与本站的所有优化可验收——溢出、发散、cp.async、Tensor Core，全在指令里现形。
