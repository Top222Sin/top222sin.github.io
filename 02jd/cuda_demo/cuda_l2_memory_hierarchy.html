L2.1 自己写高效 kernel —— 内存层次 + 合并访问 / bank conflict / 双缓冲

配套代码：cuda_l2_memory_hierarchy.cpp
对应笔记本：01CUDA基础学习.docx → L2 能写高效 kernel → 1、内存层次 global/shared/register/constant + 合并访问/bank conflict/双缓冲
这是从「能跑」(L1) 到「能写高效」(L2) 的第一道分水岭：L1 写的 kernel 跑通就够，L2 必须让每个字节都走对内存层级、避开带宽陷阱。

一、内存层次：四种”速度/容量”截然不同的空间

GPU 上有四级程序员可直接控的内存。越快越贵、越小是铁律——高效 kernel 的本质就是”把热数据塞进快的那层”。

层级 声明方式 作用域 速度 容量 典型用途
register 局部变量（自动） 单线程私有 最快（1 周期） 极少（~255 个/线程） 循环变量、累加器
constant __constant__ 全局只读、所有线程 快（有专用 cache，广播） 64 KB 偏置、缩放、查找表
shared __shared__ block 内共享、片上 很快（~1 周期） 48–164 KB/SM 分块、线程协作、双缓冲
global 普通 device 指针 全 kernel 可见 慢（~400 周期、走显存） GB 级 输入输出大数组

关键直觉：

  • register / shared 是**片上(on-chip)**，shared 比 global 快约 10–100×。
  • constant 的杀手锏不是”快”本身，而是 warp 内 32 线程读同一地址时命中同一个 cache line 并广播——一次取、32 线程共用，带宽零浪费。
  • global 容量大但每次访问都要穿过显存控制器；能不能合并成少事务决定带宽利用率。

与 NEON 对照（你已学过）：NEON 只有”寄存器 + 缓存 + 主存”三层，没有 shared 这种”程序员显式管理的片上块”。CUDA 的 shared memory 是 GPU 独有的协作层，也是 GPU 比 CPU 适合规约/分块的核心原因。

二、合并访问（coalesced access）—— 全局内存的带宽命门

为什么重要

一次 global 访存不是”取 1 个 float”，而是以 32B / 128B 段(segment) 为单位的硬件事务。一个 warp(32 线程) 同一条 load 指令：

  • ✅ 合并：32 线程访问的 32×4B = 128B 连续 → 硬件合并成 1 个 128B 事务，带宽 100% 利用。
  • ❌ 非合并（跨度访问）：线程 i 访问元素 i*STRIDE → 32 个访问散落各处 → 每个可能落到不同段，最坏 32 个事务，且每个事务只用到 1/32 字节 → 利用率低至 1/STRIDE。

近似公式

代码对照（见 cuda_l2_memory_hierarchy.cpp）

记忆法：让线程 tid 永远访问 数组[tid]（或 数组[base+tid]），不要 数组[tid*STRIDE]。矩阵场景里”行主序矩阵按行扫、按列扫”的差异，本质就是合并 vs 非合并。

三、bank conflict —— 共享内存上的隐藏减速

机制

shared memory 被切成 32 个 bank，每个 4 字节。地址 i 落在 bank = i % 32。

  • 一个周期能并行服务”每个 bank 各 1 个请求”。
  • 若同一周期多个线程访问同一 bank 的不同地址 → 必须串行完成 → 冲突路数 = 冲突线程数。

三种情况（见代码 shared_no_conflict / shared_conflict / shared_pad）

写法 访问 bank 分布 结果
✅ 无冲突 s[tid] bank(tid) = 0..31 各一 1 周期
❌ 32 路 s[tid*32] 全落在 bank 0 串行成 32 事务（慢 32×）
✅ pad 规避 s[tid*33] bank(tid*33%32)=bank(tid) 错开 无冲突

转置里的经典坑与 padding

转置 tile[j][threadIdx.x] = in[...]（读同行连续，无冲突），但写出时按 out[col*H+row] 变成按列读 tile → 线程 tid 读 tile[tid][某列]，若列距为 32 就冲突。
标准解法：声明成 tile[BDIM][BDIM+1]（多 pad 一列），让列距从 32 变成 33，与 32 互质 → 各线程落到不同 bank（见 transpose_double_buffer 的 buf[2][BDIM][BDIM+1]）。

只要”计算耗时 ≥ 预取耗时”，load 延迟被完全隐藏，SM 不空转。代价是多用一倍 shared 容量（48–164KB 通常够）。

代码落点（transpose_double_buffer）

⚠ 逻辑澄清：上例是”缓冲轮换“的骨架示意——它靠”算 cur 的同时下一轮 load 目标指向 nc”来预留重叠空间，但伪代码本身没有展示真正的异步预取指令（普通 __syncthreads() 同步的 load 不会自动与计算重叠）。真正的 load/compute overlap 需要：① cp.async/cp.async.bulk（Hopper 流水线，L3 篇展开）异步搬 tile，或 ② 专职 warp 做预取 + 显式 barrier 协议。本 demo 的 transpose 版是教学骨架（验证正确性），不要误以为它已实现延迟隐藏。

双缓冲 + 合并访问 + padding 三件套，正是 L2.4「矩阵乘分块 tiling」和 L3「异步拷贝 cp.async」的前身。理解了这里，后面的 advanced 版本只是”硬件帮你自动做预取”。

五、代码走读（cuda_l2_memory_hierarchy.cpp 主线）

  1. saxpy_constant —— c_a 用 cudaMemcpyToSymbol 写入 constant；kernel 里 y[i]=c_a*x[i]+y[i]，c_a 全线程同值走 constant 广播，x/y 按 i 合并读 global。
  2. vecAdd_coalesced vs vecAdd_strided —— 同一结果，带宽利用率差 STRIDE 倍（本例 32×）。main 里都做正确性校验。
  3. shared_no_conflict / shared_conflict / shared_pad —— 三个 kernel 结果完全一致（2·tid），但冲突版慢 32×、pad 版恢复无冲突。
  4. transpose_naive vs transpose_double_buffer —— 转置结果同为 out[c*H+r]=in[r*W+c]；朴素版无 pad + 无双缓冲，双缓冲版用 BDIM+1 pad + 两块缓冲。

所有 kernel 在真机上由 main 里的 CPU 参考值校验（沙箱无 GPU，编译运行需带 CUDA 的机器）。
