CUTLASS epilogue 组件（bias + 激活 + 写回） vs onnxruntime bias broadcast —— 工业界如何用同一套 pipeline 描述任意算子

配套文件：cuda_l3_epilogue_fusion.cpp（mini-epilogue 参考实现 + CPU 对拍）、images/fig10_epilogue_fusion.svg + cuda_l3_epilogue_fusion_diagrams.html（四联图）。
原始源码备份：_cutlass_src/（epilogue_base.h / linear_combination*.h / collective/default_epilogue.hpp）、_ort_src/gemm.cc。
本篇是 CUDA 源码线的第 3 站：上一站把 transpose/softmax/layernorm 与 CUTLASS GEMM 分块对照；本篇钻进 GEMM 的收尾段（epilogue）——正因为 epilogue 是”可编程的输出算子”，工业框架才得以用一套 MMA+pipeline 描述 GEMM / GEMM+bias / +ReLU / +GELU / +residual 等一整族算子。

一、先立问题：epilogue 为什么是”复用 pipeline”的命门

一个 GEMM kernel 分两段：

  1. MMA 段（前几站的主角）：C += A·B，把结果累加进寄存器/共享内存的 CTA 输出 tile。受 Tensor Core、tiling、双缓冲、pipeline 支配。
  2. epilogue 段：把输出 tile 做最后的逐元素加工并写回全局内存。这一步要做的往往是 D = α·accum + β·C + bias，再套一个激活（ReLU/GELU/Sigmoid）、再决定写 D 还是写 D+T（残差）。

关键洞察：MMA 段对所有”GEMM 系算子”几乎一样，差异全在 epilogue。所以只要把 epilogue 做成”可替换的计算 functor”，同一套 MMA+pipeline 就能服务一整族算子——这正是 CUTLASS 与 ORT 共同的工程答案，只是落地方式不同。

二、CUTLASS 的 epilogue：把”输出算子”做成模板参数

2.1 写回骨架 EpilogueBase（epilogue_base.h:95-228）

EpilogueBase 只负责把 warp 级的累加片段经共享内存重排成全局内存的规整布局，再合并写回。它定义：

  • SharedStorage（含 AlignedBuffer，带 Padding 规避 bank conflict——回扣 L2.1）；
  • WarpTileIterator 把每个 warp 的累加 fragment 写进 SMEM；
  • warp 在 threadblock tile 内的坐标 (warp_m, warp_n)（add_tile_offset）。

它本身**不含任何”算”**，只管”搬+写”。真正”算”的是注入的 OutputOp。

2.2 逐元素计算 LinearCombination（linear_combination.h:217-250）

这就是 2.x 的默认输出算子：

  • source = GEMM 的 C（bias 就藏在 C 里——当 C 是广播向量时即 bias）；
  • alpha/beta 可来自标量、指针、甚至 per-group 数组（Params 里的 alpha_ptr_array，支持分组不同缩放）；
  • is_source_needed() 决定要不要读 C（β==0 时直接跳过，省一次全局读，回扣 L2.1 合并/省带宽）。

2.3 任意融合 LinearCombinationBiasElementwise（linear_combination_bias_elementwise.h:344-348）

这是”描述任意算子”的核心。其 operator() 一句话：

  • bias 广播：V 是一个 ElementVector，epilogue 按 Broadcast 类型（逐行/逐列/标量）只取一次、广播到 tile；
  • 任意激活：ElementwiseOp 是模板参数（Identity / ReLU / GELU / Sigmoid / …）。换激活 = 换一个类型实参，MMA 与写回 pipeline 一行不改；
  • **skip_elementwise_**：多 K 段串行归约时，中间段只做 α·accum+β·C、最后一段才激活（set_k_partition，:248-256）——一个算子内部也要分阶段；
  • 还支持同时写 Z 和 T（残差/中间量，kStoreT），这是 fused residual-add 的工业写法。

2.4 3.x 的极致：visitor 模式 DefaultEpilogue（collective/default_epilogue.hpp:154-252）

CUTLASS 3.x 用 CuTe 把 epilogue 升格为 Epilogue Visitor Tree（EVT）：epilogue 不再是单一 OutputOp，而是一棵由节点组成的计算图——LoadC → BiasAdd → Activation → StoreD (→ StoreT)。每个节点是同一个 accumulators fragment 上的访客。

于是”GEMM + LayerNorm + 残差 + 写回”这种复合算子，只是换一棵 visitor 树，MMA 主循环与线程映射完全复用。这把”同一套 pipeline 描述任意算子”做到了语法级。

三、ORT 的 bias broadcast 巧法（gemm.cc:100-142，逐行解析）

ORT 的 Gemm 不手写 fused kernel，而是复用 cublasLt 库自带的 epilogue（D = α·A·B + β·C），把 bias 塞进 β·C 项”免费”加上：

巧在哪：

  • 没有独立的”加 bias kernel”、没有额外的全局访存往返；
  • bias 先灌进 Y（一次预填），GEMM 的库 epilogue（β·C 项，C 这里就是 Y）顺手完成 accum + bias；
  • 这正对应 L2.3 的算术强度思想：把逐元素算子融合进 GEMM，省掉 1–2 次 读 D→写 D 的 DRAM 往返（memory-bound 下直接提速）；
  • 与 CUTLASS LinearCombination 的公式 D = α·accum + β·C 是同一个数学结构——ORT 用库的 epilogue 实现，CUTLASS 用自己模板化的 OutputOp 实现。

注：带激活的融合（Gemm+FastGelu/BiasGelu）ORT 走另一条 FusedMatMul 路径再叠一次 elementwise kernel；CUTLASS 则直接在 epilogue visitor 里一次做完——殊途同归。

四、同一条 pipeline，描述任意算子（对照表）

目标算子 CUTLASS 怎么”换” ORT 怎么”换” 共同点
GEMM OutputOp = LinearCombination（β=0，不读 C） cublasGemm β=0 MMA 主循环不变
GEMM + bias OutputOp = LinearCombinationBiasElementwise（C=bias 广播） 预填 Y=bias + cublasGemm β≠0 复用 α·accum+β·C 结构
GEMM + bias + ReLU 把 ElementwiseOp 换成 ReLU（模板实参） FusedMatMul 叠 ReLU kernel 改”输出算子”，不动 MMA
GEMM + bias + GELU + 残差 EVT 访客树 LoadC→Bias→GELU→AddResidual→Store 多个融合 kernel 串联 同一 pipeline，算子=插件
逐行/逐列 bias Broadcast 类型决定 V[i] 取值 (N,)/(M,1) 走不同预填分支 bias 广播 = 一次取、全 tile 用

一句话总结：工业界把”算子差异”收敛到输出算子（epilogue）这一个可替换点——CUTLASS 在类型系统里做（模板/visitor），ORT 在调用约定里做（β·C 复用 + 库能力），但两者都守着”MMA+pipeline 唯一、epilogue 可编程”这一条原则。

五、与前面 L2 的串联

  • L2.1 内存层次 / 合并 / bank conflict：EpilogueBase::SharedStorage 照样带 Padding 规避 bank conflict；is_source_needed()=false 时跳过读 C，省一次全局读 = 提 AI（回扣 L2.3）。
  • L2.2 warp / occupancy：epilogue 是逐 warp 处理输出 tile 的子集，和 MMA 共用 occupancy 预算；重激活（”heavy” functor，kIsHeavy）会被抽成不内联以压代码体积——与前几站”寄存器压力/occupancy”同源。
  • L2.3 Roofline / compute vs memory-bound：把 bias/激活融进 epilogue，砍掉输出张量 读 D→写 D 的冗余往返——对输出张量 D 是 5×→1×（见 analyze_fusion()）。但要诚实：独立 GEMM 的总流量受 A·B 读取（2·M·N·K）支配，融合在整 op 层面占比很小、单看提速有限；真正的收益在算子链（GEMM→Norm→残差每一步都落盘会反复读写中间张量，epilogue 串起来即免落盘）。这恰好说明 L2.3 的”提 AI/减 DRAM”在链式算子里才放大量级。
  • L2.4 tiling / 双缓冲 / pipeline：epilogue 站在 MMA 的”下游”，共享同一套 kStages 流水线状态与输出 tile 迭代——这正是”同一套 pipeline”的运行时含义。

六、自检（动手验证）

  1. 编译 CPU 版（无 GPU 也能跑）：g++ -O3 -std=c++17 cuda_l3_epilogue_fusion.cpp -o ep && ./ep
    → 预期打印 [verify_on_cpu] PASS，并给出 pipeline 与 ORT β-trick 两组的 Z=relu(accum+bias) 数值，二者一致；analyze_fusion() 会打印诚实结论：输出张量 D 往返 5×→1×，但整 op 占比很小、收益在算子链。
  2. 真机 GPU 版：nvcc -O3 -std=c++17 cuda_l3_epilogue_fusion.cpp -o ep && ./ep
    → 同一 CPU 校验通过；gemm_bias_act_epilogue kernel 结构与 MiniOutputOp 一一对应，可在 main() 里 cudaMemcpy 后对拍。
  3. 读源码对照（已备份）：
    • CUTLASS linear_combination_bias_elementwise.h:344-348 → 本文件 MiniOutputOp::operator()；
    • CUTLASS epilogue_base.h:137-187 → 本文件 epilogue_pipeline（输出 tile 迭代 + 写回概念）；
    • ORT gemm.cc:100-142 → 本文件 ort_bias_prefill + ref_gemm_with_ort_beta。
  4. 思考：若要让本文件的 epilogue_pipeline 也支持”逐元素 GELU + 残差写 T”，最小的改动在哪？（提示：把 MiniOutputOp 换成带 act 与 store_T 的版本，对应 CUTLASS 的 ElementwiseOp + kStoreT。）
