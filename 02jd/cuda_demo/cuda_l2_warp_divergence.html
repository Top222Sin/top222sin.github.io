L2.2 自己写高效 kernel —— warp 概念 / 分支发散 / occupancy / 寄存器压力

配套代码：cuda_l2_warp_divergence.cpp
对应笔记本：01CUDA基础学习.docx → L2 能写高效 kernel → 2、warp 概念、分支发散、occupancy、寄存器压力
这是 L2 的第二道分水岭：L2.1 解决”数据走对内存层级”，这一节解决”指令怎么在 SM 上排布才不空转”。四个概念环环相扣：warp 是调度单位 → 分支发散让 warp 内串行 → occupancy 决定 SM 上能塞多少 warp → 寄存器压力又反过来压低 occupancy。

一、warp 概念 —— 硬件调度的最小单位是 warp，不是线程

你写 <<<grid, block>>>，但 SM 真正调度、发射的不是单个线程，而是 warp（32 线程一组）。

  • 一个 block 被切成 ceil(blockDim / 32) 个 warp。block=256 → 8 个 warp；block=64 → 2 个 warp。
  • 同一 warp 内 32 个线程共享一个 PC（程序计数器），锁步(lockstep)执行同一条指令 —— 一条指令发射，32 个 lane 同时跑这一步。
  • 线程在 warp 内的编号叫 **lane_id (0..31)**；block 内第几个 warp 叫 warp_id；等价内建函数 __lane_id()（本文件手算以便校验与兼容）。

为什么重要：warp 是”并发粒度”。后面的分支发散、occupancy 全建立在”warp 才是执行/调度单元”这件事上。它和 NEON/SIMD 不同——SIMD 是”一条指令广播到固定宽度的向量通道”，而 SIMT 的 warp 是”调度器每次挑一个 warp 发射，warp 内 32 线程各走自己那份数据”，更灵活，但代价是分支要按 warp 对齐。

验证：本文件 [1] 用 4 block×256=32 warp，校验 lane=t%32 / warp_in_block=t/32 / global_warp 连续，全部 PASS。

二、分支发散（branch divergence）—— 同一 warp 走不同路径 = 两条路径串行

如果 warp 内一部分 lane 进 if、另一部分进 else，硬件不能让两条路径并行，而是：

⚠️ 该 warp 耗时 = 两条路径耗时之和（不是取 max！）。这就是”看不见的性能黑洞”——代码看起来只有 if/else，实际一个 warp 把两条路都跑了一遍。

教学难点：发散是性能问题，沙箱无法计时

本文件用 __ballot_sync 把发散”显影”成可校验数字，无需计时：

  • diverge_by_lane：谓词依赖 threadIdx.x % 2 → 一个 warp 半真半假 → popc == 16 → 一旦以它分支，必然发散（[2a] 校验 popc 全为 16）。
  • coherent_by_warp：谓词按全局序号对齐到 warp 边界（g < n/2，且 n 是 64 的倍数）→ 一个 warp 要么全真(popc=32)要么全假(popc=0) → 不会发散（[2b] 校验：g<128 报 32、g≥128 报 0）。

规避法则：把”会分裂 warp 的条件”换成”按 warp 对齐的谓词”。典型坑：

  • if (threadIdx.x % 2 == 0) ❌（warp 内分裂）
  • if (global_tid < N/2) ✅（以 warp 的 32 为界，落点整 warp 一致）
  • 数据相关的 if (val > 0) 若 val 在 warp 内分布随机 → 仍发散，此时用 __syncwarp/重排或换无分支写法（如 val = (val>0)?val:0 虽仍谓词但已无两条重路径差异时可接受，重路径差异大才亏）。

三、occupancy（占用率）—— 一个 SM 上能同时驻留多少 warp

occupancy = 活跃 warp 数 / SM 最大 warp 数。它受三道天花板里最紧的那个限制：

限制来源 公式 说明
寄存器 每线程寄存器 × 每 block 线程数 × block 数 ≤ 寄存器文件 寄存器用太多 → 每 SM 装不下几个 block
shared mem 每 block shared × block 数 ≤ SM 共享内存 共享内存开太多同理
线程/block 上限 block 数 ≤ 每 SM 最大 block 数(通常 32) / 线程数 ≤ 每 SM 最大线程数(如 2048) 结构性上限

为什么 occupancy 重要？低 occupancy = 同时驻留的 warp 少 = 遇到长延迟(如 global 访存 ~400 周期)时，SM 没别的 warp 可切去隐藏延迟 → 空转等待。高 occupancy 给调度器更多”切换余地”去掩盖延迟。

__launch_bounds__ 是给编译器的硬约束

含义：要求每 SM 至少塞下 4 个 block。编译器据此把每线程寄存器压到
寄存器文件 / (minBlocksPerSM × maxThreadsPerBlock) 以内，从而换得更高 occupancy。

  • minBlocksPerSM 大 → 逼出更少寄存器 → occupancy 高，但每线程可用寄存器少（可能 spill，见第四节）。
  • minBlocksPerSM 小/不写 → 编译器自由用寄存器 → 单线程快，但 occupancy 可能低。

量化（真机用 Occupancy API）

本文件 [3] 调用 cudaOccupancyMaxActiveBlocksPerMultiprocessor 对 occ_free(无约束) 与 occ_bounded(256,4) 各算一次，再算 occupancy = blocks*256 / (maxWarps*32)。典型输出类似：occ_free=0.50, occ_bounded=1.00，说明压寄存器把 occupancy 从 50% 拉满。

经验：先让 kernel 跑通，profiling 发现 occupancy 低且被寄存器限制时，再用 __launch_bounds__ 提；别一上来就乱加，可能适得其反（寄存器太少导致 spill，更慢）。

四、寄存器压力（register pressure）—— 寄存器不够就溢出到 local memory(= 慢!)

每个线程可用的寄存器远非无限：SM 寄存器文件总量 ÷ 同时驻留的线程数。常见 GPU 每 SM 约 65536 个 32-bit 寄存器。

  • kernel 局部变量太多/编译器不够用 → 溢出(spill)到 local memory。而 local memory 本质是 global 显存里的一块！spill 一来，本该 1 周期的寄存器访问变成显存往返（~400 周期），性能暴跌。
  • 高寄存器压力还会压低 occupancy（和第三节同一道天花板），形成”慢 + 少并发”的双重打击。

演示与规避

本文件第四节 high_pressure(8 个独立累加器 + 循环，逼编译器多用寄存器) 与 low_pressure(同计算，但 __launch_bounds__(256,8) 逼编译器压低每线程寄存器)。两者数值结果完全一致（CPU 参考 cpu_ref 校验 PASS），区别只在”背后用多少寄存器”。

怎么看压力：编译时加 --ptxas-options=-v，看每个 kernel 的 registers 字段：

  • high_pressure 的 registers 通常更大，可能伴随 spilled registers > 0；
  • low_pressure 因 launch_bounds(256,8) 强制压低，registers 更小、spill 更少。

权衡口诀：寄存器太少 → spill 到显存变慢；寄存器太多 → occupancy 低、延迟藏不住。最优值在中间，靠 profiling 找。

五、代码走读（cuda_l2_warp_divergence.cpp 主线）

  1. inspect_warp — 把 lane / warp_in_block / global_warp 写回，CPU 校验”t%32 / t/32 / 连续“三层关系，[1] PASS。
  2. diverge_by_lane vs coherent_by_warp — 都用 __ballot_sync 显影发散：
    • 前者谓词依赖 lane → 每 warp popc=16（半真半假）→ 必发散；
    • 后者谓词按 g<n/2 对齐 warp 边界 → popc=32 或 0 → 不发散。
      两个 kernel 都用”重/轻两条路径”把分支结果编码进输出低位，验证分支逻辑本身正确。
  3. occ_free vs occ_bounded(256,4) — [3] 用 Occupancy API 量化：bounded 因压寄存器，occupancy ≥ free（真机实测）。
  4. high_pressure vs low_pressure(256,8) — [4] 数值都对（对照 cpu_ref），差异仅在寄存器用量；编译加 --ptxas-options=-v 即可见。

六、OpenCL 对照（概念完全同构）

CUDA OpenCL 备注
warp(32 线程锁步) wavefront / sub-group AMD wavefront=64，Intel=32；OpenCL 2.0+ 有 sub-group 概念，等价 warp
lane_id / __ballot_sync sub_group_ballot / 厂商扩展 sub-group 内掩码投票
分支发散 sub-group 内谓词混合 → 两路径串行 同样存在，规避思路一致
__launch_bounds__(max,min) 无直接等价 靠 work-group size + 编译选项间接控制
occupancy compute unit 上能驻留多少 wavefront 受 private mem / local mem / 线程数限制
寄存器压力 / spill private memory 溢出到 global OpenCL 也称”private 溢出”
__sinf / __cosf native_sin / native_cos fast math 内建
__syncthreads() barrier(CLK_LOCAL_MEM_FENCE) 同步原语
