L3.1 架构级第一站：kernel fusion + 异步拷贝(cp.async/memcpy_async) + pipeline

本文件是 cuda_l3_fusion_pipeline.cpp 的配套讲解。三者是一条主线而非三个散点：
为什么融（fusion）→ 怎么重叠（async copy）→ 怎么编排（pipeline）。
图示：images/fig12_l3_fusion_pipeline.svg（四联图），浏览器完整预览 cuda_l3_fusion_pipeline_diagrams.html。

0. 这一站解决什么

L1/L2 关心「一个 kernel 内部怎么写对、写好」。L3 关心多个 kernel 之间怎么组织才能逼近硬件峰值：

  • 朴素写法里，算子 A 算完把结果写回全局内存，算子 B 再读回来 → 中间张量在全局内存里做了无意义的「写出来又被读回去」往返。
  • 同时，GPU 计算快、访存慢，MMA/Tensor Core 一个时钟能吃好几条指令，但等数据从全局内存飞过来要几百周期 → 计算单元在「等数据」。

L3 第一个组合拳就是：用 fusion 消灭中间往返，用 cp.async / pipeline 把「取数」和「计算」在时间上重叠，把访存延迟藏起来。

1. Kernel fusion（算子融合）

1.1 例子：逐元素链 y = GELU(scale·x + bias)

写法 kernel 数 全局内存行为 全局流量（N 元素, float=4B）
naive（拆 3 个） 3 每 stage 读上一输出 + 写自身输出 读 3N·4 + 写 3N·4 = 6N·4
fused（合 1 个） 1 只 1 读(x) + 1 写(y) 读 1N·4 + 写 1N·4 = 2N·4
  • naive 的 3 个 kernel：t1=x*scale → t2=t1+bias → y=gelu(t2)，t1、t2 都落了全局。
  • fused 把三步在寄存器里一次做完，t1/t2 从不落全局。

对应代码：fusion_traffic_naive(N,3) vs fusion_traffic_fused(N)，N=1M 时全局流量 3× 降低；verify_fusion() 用 N=1024 确认 fused 数值与 naive 串联逐元素一致（[verify_on_cpu] PASS）。

1.2 fusion 省的不只是带宽，还有 launch

每个 kernel 启动有固定开销（~微秒级，含网格配置、依赖检查）。把 3 个合成 1 个，launch 次数 3→1，对小算子 / 高调用频次（如推理里大量 1×1 小 tensor）收益明显。

1.3 诚实边界（不要神话 fusion）

  • 不是所有算子都能融。逐元素（per-element，线程间无通信）最容易融；需要跨线程规约的（reduce / layernorm 的均值方差 / softmax 的分母）要先在 shared/寄存器里把规约做完再融，否则破坏融合。
  • 融太多会挤占寄存器/共享，导致 occupancy 下降、反而变慢。融合是「减少往返」与「资源压力」的权衡，要 profile 说话（回到 L2.3 的 Nsight）。
  • 真正的收益来自「免落盘」：前面 L2 工业线第 3 站 analyze_fusion() 已验证——融合对整 op 的算术强度几乎不变，它省的是「中间张量在全局内存的读写往返」，不是让计算变少。

2. 异步拷贝：cp.async / memcpy_async

2.1 普通 load 的瓶颈

普通 __global__ 读：ld.global 把数据经寄存器搬进线程，再 st.shared 写共享。问题有二：

  1. 数据经过寄存器 → 占寄存器、且线程被这条 load 阻塞到数据回来；
  2. 发射 load 的线程在等数据时干不了别的事。

2.2 cp.async（PTX，Ampere SM_80+）

cp.async 让一块专门的异步拷贝引擎直接把数据从全局内存搬到共享内存：

  • 不经过任何线程的寄存器；
  • 发射线程立刻继续（不等数据），数据由引擎在后台飞。
  • .ca/ .cg：缓存策略（all-levels / global-only）。
  • 第 3 操作数只能是 4 / 8 / 16 字节。
  • Hopper(SM_90) 用 cp.async.bulk（TMA） 一次搬整块并自动处理边界/padding，语义一致。

3. pipeline：把「取数」和「计算」重叠

光有「异步拷贝」还不够——得有人编排：在消费第 i 块数据时，提前把第 i+1 块搬进来。这就是 pipeline / 软件流水线。

3.1 核心思想：k 个缓冲 + 生产者/消费者

  • 准备 k 个共享缓冲（= CUTLASS 的 kStages）。
  • 生产者 warp 负责用 cp.async 把全局操作数搬进缓冲（不阻塞）。
  • 消费者 warp 等 wait_group 后，用缓冲里的数据做 MMA/计算。
  • 约束：缓冲 i 被搬入前，必须等上一次用它的 tile i-k 算完释放。

于是时间线上：消费 tile i 的同时，生产者已经在搬 tile i+1。访存延迟被「藏」在计算后面。

3.2 量化：时间线仿真（pipeline_time() vs naive_time()）

模型：N 个互相独立的 tile，每 tile copy=Tc、compute=Tm，k 个缓冲。仿真 N=200：

场景 naive k=1 k=2 k=4 k=8
balanced Tc=Tm=1 400 400 ~222 ~211 ~206
compute-bound Tc=1,Tm=3 800 800 ~420 ~406 ~402
memory-bound Tc=3,Tm=1 800 800 ~420 ~406 ~402

（数值由 run_sims() 实际打印；上表为量级示意，精确值以程序输出为准。）

3.3 诚实结论：收益有上限，且只在「有延迟可藏」时划算

  • 均衡 / 访存主导时，重叠把每 tile 的有效耗时压到接近 max(Tc,Tm)，加速比逼近 2×。
  • 计算已占主导（compute-bound）时，瓶颈本就是算力而非访存，没多少延迟可藏，加速比趋近 1×。
  • 所以 fusion / pipeline 对「带宽受限」算子最划算，对已经 compute-bound 的算子收益有限——这正好和 L2.3「compute-bound vs memory-bound」的诊断闭环。

代码里 run_sims() 末尾打印了同样的解读。注意：本仿真是「单拷贝引擎 + 独立 tile」的简化模型，目的是给出正确量级与趋势，不是某块具体 GPU 的精确测时。

4. 三者如何串成一条主线

一句收束：fusion 减少「要搬多少」，cp.async+pipeline 减少「搬的时候干等」——两者都服务于同一个目标：让昂贵的算力别在访存上空转。
