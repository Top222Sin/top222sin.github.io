review_0820_review — 对 review_0820.md 所列“已落地”实现的复查意见

复查对象：02jd/review_0820.md 及其引用的 L4 扩展实现（control / pid / Jacobian / KF / cali / LS / cuda / neon 八个 demo）。
复查方法：静态检查 review_0820.md 与各 .md / .cpp 的对应关系、可编译性、数值一致性和“已落地”状态。

一、总体结论

review_0820.md 的选题方向和知识结构是合理的：它识别出的 P0/P1/P2 缺口确实是工业界高频知识点，并且大部分新增笔记（.md + .cpp + .html + svg 四件套）在教学内容和推导结构上写得扎实、可读性强，跨 demo 互引也很有价值。

但当前不能直接把 review_0820.md 当作“全部已落地且验证通过”的报告，主要原因是：

  1. 部分 C++ 源码存在明显编译错误，与文档中“确定性重现 / PASS”的说法矛盾；
  2. review_0820.md 内部状态滞后/不一致，有些已经落地的文件没有被标记，有些详细章节仍停留在“建议落点”；
  3. 少量数值与实现文档不一致，需要统一；
  4. 部分“已落地”属于 CPU 语义模型而非真实 CUDA/NEON 硬件实现，报告应更明确边界，避免读者误以为是真机验证。

二、必须优先处理的问题（P0）

2.1 C++ 源码可编译性

以下问题来自源码静态检查，按当前代码看必然导致 g++ -std=c++17 / clang++ 编译失败：

文件 位置 问题
KF_demo/kf_l4_enkf_mhe.cpp 第 53–58、279–280 行 matvecM() 声明返回 Mat，实际 return y; 返回 Vec；随后 matvec() 又返回 matvecM(A,x)（Mat → Vec），f_obj() 里也把 matvecM 当 Vec 用。属于 Mat/Vec 类型混淆，必然编译失败。
control_demo/ctrl_l4_hinf.cpp 第 44–45 行 static double rhoCx2(const Cx A[2][2]){ 连续出现两次，函数体前多了一个重复函数头，语法错误。
control_demo/ctrl_l4_fbl.cpp 第 74、85 行 定义的是 chkBool，第 85 行调用的是 chk_bool，标识符不一致，编译失败。

建议：修复上述问题后，在能运行 build.py 的 Linux/沙箱环境中对全部 L4 cpp 做一次全量编译，并把编译结果作为“PASS”的前提。

2.2 review_0820.md 状态与文件清单不同步

以下情况会误导读者：

  • cuda Hopper 已落地但报告未标记：cuda_demo/cuda_l4_hopper_tensorcore.cpp/.md 已存在，且文档称 17 项检查 PASS；但 review_0820.md 总览表第 46 行仍写“TensorCore 篇止于 sm_80/fp16/tf32”，P1 路线也未标 ✅。
  • LS 子空间辨识状态矛盾：总览表第 47 行仍写“仅 ARX（OE 类）”，但 P1 路线第 181 行已写“子空间辨识 N4SID（✅ L4.7）”。
  • pid P2 详细章节未更新：总览表第 49 行已把 FOPID/模糊 PID/IAE/MIMO 标 ✅，但分 demo 详述 2.2（第 79–80 行）仍写“建议落点”，没有同步。
  • cali P2 详细章节未更新：总览表第 50 行已把自标定/结构光/RGB-D/多相机 rig 标 ✅，但分 demo 详述 2.5（第 111–112 行）仍写“建议落点”。
  • “CUDA 统一内存与 Graphs”表述过宽：review_0820.md 第 23 行写“CUDA 统一内存与 Graphs ✅已落地(cuda_l4_cuda_graphs)”，但实际文件只覆盖 CUDA Graphs，没有统一内存（Unified Memory）内容。

三、数值/文档一致性问题（P1）

不一致 位置 说明
SME2 乱序累加误差 review_0820.md 第 222 行写 err≈4.4e-16；neon_demo/neon_l4_sme2.md 第 81 行写 F3 err≈6.0e-8 二者数量级明显不同，应核对实际运行结果后统一。
BF16/FP16 精度数值 review_0820.md 第 221 行写 fp16=3.47e-4 / bf16=3.33e-3；neon_demo/neon_l4_bf16.md 第 54 行写 fp16=3.88e-4 / bf16=3.81e-3 若依赖 RNG/随机矩阵，报告中不应固化精确数值；若不依赖，则必须与 md 完全一致。

另外 review_0820.md 第 145 行 neon_l4_simd_abstract 行尾多了一个多余列，建议顺手修正 Markdown 表格格式。

四、关于“已落地”的边界说明（P2）

  • cuda_l4_* 的多数 L4 文件（Graphs、Hopper、cuFFT/cuSPARSE/cuRAND、compute-sanitizer、grouped GEMM）实际是 host 端 CPU 语义模型 + #ifdef __CUDACC__ 真机片段，不是可运行在真实 GPU 上的 CUDA 实现。
  • neon_l4_bf16 / neon_l4_sme2 也主要是 指令语义模型 + ARM intrinsic 守卫骨架，并非在 ARM 真机上跑出的结果。
  • 这些文件本身在 .md 中有“本沙箱无 GPU / 无 nvcc / 无 ARM”的诚实说明，这是好的；但 review_0820.md 的“✅ 已落地”容易让读者误以为是真机/真实库验证。建议在报告中统一标注为 “CPU 语义模型 + 真机片段” 或 “待真机验证”。

六、改进建议

  1. 先修编译错误，再谈 PASS：

    • 修复 kf_l4_enkf_mhe.cpp 的 Mat/Vec 类型；
    • 删除 ctrl_l4_hinf.cpp 重复函数头；
    • 将 ctrl_l4_fbl.cpp 的 chk_bool 改为 chkBool（或统一命名）。
    • 之后运行各 demo build.py，确保 === N passed, 0 failed === 是从真实编译运行得到的。

  2. 同步 review_0820.md 与文件清单：

    • 在总览表和 P1 路线中标记 cuda_l4_hopper_tensorcore 已落地；
    • 统一 LS 子空间辨识的状态；
    • 更新 2.2 pid 和 2.5 cali 的详细章节，使其与总览表一致；
    • 修正“CUDA 统一内存与 Graphs”的表述。

  3. 统一数值口径：

    • 对 RNG 相关结果，报告只写结论趋势，不写具体到 4 位小数的数值；
    • 对固定数值，确保 review_0820.md 与对应 .md 完全一致。

  4. 明确“教学模型”与“真实硬件实现”的边界：

    • 在报告/文档中使用“CPU 语义模型”、“真机片段待验证”等词；
    • 避免把 cuda_l4_*、neon_l4_* 的 host 模拟结果等同于真实 CUDA/NEON benchmark。

  5. 增加自动化校验：

    • 可在仓库中加入一个简单脚本，扫描 review_0820.md 中所有 ✅ 已落地 对应的文件是否存在；
    • 对纯 C++ 文件执行 g++ -std=c++17 -fsyntax-only 或 build.py，防止类似问题再次混入。

七、结论

review_0820.md 作为“工业知识点查漏报告”是很有价值的，新增内容的方向、深度和互引设计总体合理；但当前不能将其视为全部实现已通过验证的最终报告。至少需要先修复本文列出的三个 C++ 编译错误，并同步报告状态与文件清单、统一数值，然后才能把“已落地 / PASS”作为可信结论。
