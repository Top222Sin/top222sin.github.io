02jd 内容充实计划（Enrichment Plan）

目标：在不破坏 Obsidian 跳转的前提下，把 8 个 demo 的 .md 从”框架齐全但单薄”充实到”内容饱满、可深读”。
每个 demo 补充完成后，用 qinzhiai gpt-5.6-sol 做 review 校验闭环（qinzhiai-review-workflow 技能），修复后逐条核对。

二、充实标准（每篇 md 对标 neon 结构）

一篇”充实”的 demo 笔记应包含以下 8 个元素（现有已具备的保留，缺的补齐）：

  1. 公式推导过程：不只给结论公式，给出从定义到结果的推导链（离散化、增益推导、协方差递推等）
  2. 内联 SVG 图 1-3 张：方框图 / 响应曲线 / 对比图（放 images/，md 内 ![]() 内联，Obsidian 原生渲染）
  3. 真实工程源码落点：
    • control/pid/KF/cali → PX4 源码（src/modules/...，给文件+函数）
    • LS/Jacobian → OpenCV / Ceres / PX4 对应模块
    • neon/cuda → ncnn/MNN/ONNX Runtime 对应 layer 实现
  4. 对比表 / 决策表：何时用 A 何时用 B（如：前向 vs 后向欧拉、EKF vs UKF、直接法 vs im2col）
  5. 工程坑（真实踩过）：与 ctrl_l1_bode 的”相位扫描必须解缠绕”同类，每条坑给成因+解法
  6. 变体与边界条件：适用域、失效模式、参数边界（如 fc 与 fs 关系、Q/R 数量级）
  7. 自检：保留现有”你会看到什么”输出样例 + 动手实验
  8. 导航完整：保留 frontmatter 五字段、[[下一篇]]/回 README wikilink；新增跨 demo 引用时用 [[目标|显示名]]

量化目标：薄弱 demo 篇均从 ~2KB 提升到 ≥5KB（content 深度对齐 neon 的 40-60%），全文公式/表格/图数可复算。

三、执行顺序（按薄弱优先 + 依赖递进）

每个 Phase 完整流程：重读该 demo 全部 md + 对应 cpp → 逐篇充实（不改文件名/不动 frontmatter 结构）→ 补 SVG 图 → 更新 README MOC → gpt-5.6-sol review 全 demo → 修复 + 逐条核对处置表 → git commit（dev 分支）

Phase demo 篇数 主题依赖 预计充实量
P1 control_demo 17 控制基础（最薄，先打底） ~35KB
P2 pid_demo 16 依赖 control 的频域/稳定性 ~35KB
P3 Jacobian_demo 22 运动学基础 ~50KB
P4 KF_demo 21 依赖 Jacobian（EKF 用雅可比） ~50KB
P5 cali_demo 19 手眼标定依赖运动学 ~40KB
P6 Least_squares 22 标定/滤波的共同数学地基 ~45KB
P7 cuda_demo 抽查 21 已充实，只补个别 L1 ~10KB
P8 neon_demo 抽查 8 标杆，抽查+链接补全 ~5KB

顺序理由：control → pid 同属控制链；Jacobian → KF 是”雅可比 → EKF 线性化”依赖；cali 手眼标定依赖 Jacobian；LS 作为标定与滤波的共同数学基础放倒数（已有内容相对多，且其余 demo 会反哺其引用）。

四、Obsidian 格式保障（硬约束）

  • 文件名一律不改（所有 [[wikilink]] 依赖文件名，改名 = 全库链接维护，禁止）
  • frontmatter 五字段保留：level / topic / demo / type / status，新增笔记按 OBSIDIAN_使用指南.md 模板
  • 新图放各 demo images/ 下，md 内 ![]() 内联（Obsidian 原生渲染 SVG）
  • 新链接统一 [[目标文件名|显示文字]]；跨 demo 引用允许（图谱会形成簇间连线）
  • 数学公式沿用 Unicode 文本风格（仓库现有约定），不引入 LaTeX 大改
  • 补充完成后 grep 校验：所有 [[...]] 目标文件存在、无断链

五、gpt 校验闭环（每 demo 强制）

  1. review：curl qinzhiai /v1/chat/completions（gpt-5.6-sol，key 见技能 qinzhiai-review-workflow），审查维度 = 数学正确性 / 文档-代码一致性 / PX4-ncnn 源码引用真实性 / 链接完整性；长文档分段送审，意见落盘 <demo>_demo_review.md
  2. 修复：确定性错误 100% 修复；轻微问题视风险修复
  3. 逐条核对：review 意见作为清单逐条对照原文档，标记 已修/遗漏(补修)/有意不修(理由)，输出处置表
  4. 验证：有 g++ 环境的 demo 跑 build.py 确认 cpp 仍 PASS（md 充实不改 cpp，但若发现文档-代码不一致，以 cpp 实际行为为准修 md）
