TVM(OSDI 2018)论文精讲: 端到端深度学习编译器

TVM(OSDI 2018)论文精讲: 端到端深度学习编译器

论文: TVM: An Automated End-to-End Optimizing Compiler for Deep Learning, Tianqi Chen et al., OSDI 2018 (arXiv:1802.04799v3)
视角: 模型部署 / 推理引擎工程师。所有加速比、结构名、图表编号均以原文为准;论文之后的生态演进已单独标注。

0. 结论先行(30 秒)

  • TVM 的骨架是”两级优化 + 一个自动调优器”: 图级(算子融合 / 布局变换 / 静态内存规划)+ 算子级(张量表达式 + 调度原语),再叠加 ML 成本模型驱动的调度搜索器。
  • 核心抽象是”计算与调度分离”(继承 Halide),TVM 的增量是把硬件 intrinsic 也从调度里解耦(tensorization),于是同一份算子描述能落到 CPU / GPU / FPGA 加速器。
  • 关键数字(全部来自原文): 端到端相对既有框架(含手工优化库)加速 1.2×–3.8×;算子融合 1.2×–2×;成本模型单次预测 0.67 ms;FPGA 加速器上被卸载的卷积层 40×;延迟隐藏让峰值计算利用率 **70% → 88%**。
  • 对部署人的意义: 当推理框架里没有目标算子的优化实现时,DSL + 代码生成是”止损”手段;而”成本模型”和”基准测试”是两种不同的东西 —— 前者用来排序候选,后者用来定真值。

1. 要解决的问题: 为什么”框架 + 算子库”不够用

论文开篇把矛盾拆成三点：

1) 图级优化”看不见”硬件,算子库”只认少数后端。 TensorFlow / MXNet / Caffe / PyTorch 靠计算图 IR 做自动微分、内存管理等优化,但图级优化太高层,处理不了后端相关的算子级变换;于是把目标相关优化甩给厂商算子库(cuDNN / cuBLAS / MKL)。这些库需要大量人工调优,特化、不透明、难以跨硬件移植。

2) 图级与算子级之间存在一个”二选一”陷阱。 框架做图优化常会产生新算子(如融合后的 conv+bn+relu),此时只能二选一: (a) 放弃产生新算子的图优化 —— 因为库里没有实现;(b) 用未优化的 fallback 实现这些新算子 —— 收益被吃掉。论文原话点得很直白: 图级优化**”其效果上限就是算子库提供了什么”;而算子种类 × 布局 × 数据类型 × 加速器 intrinsic 的组合是组合爆炸**的,靠手工写 kernel 不可持续。

3) 硬件分歧 + 巨大搜索空间。 CPU 的存储层级由硬件隐式管理(SMT / 预取),GPU 靠 warp 快速切换,TPU 类加速器则偏好更精简的控制、把调度复杂度交给编译器栈,甚至要求编译器显式插入流水依赖同步来隐藏访存延迟（TVM 论文图 1）。同时,访存模式 × 线程组织 × 新 primitive 的组合让配置空间大到”黑盒自动调优无法承受”,而给每种硬件手写一个精确 cost model 同样不现实。

为什么这对做模型部署的人重要: 你遇到的”某算子没有优化实现,只能退回 CPU / naive 版本”不是工程偷懒,而是第 2 条的结构性后果。理解它,才能判断什么时候该升级推理引擎、什么时候该上 DSL 生成 kernel。

2. TVM 的关键分解(先看骨架)

论文的总览图可以归纳成三个阶段、两个层级:

层级 优化对象 硬件相关性 论文位置
图级 整个计算图的结构(融合、布局、内存) 基本无关,收益最大 （TVM 论文）
算子级 单个张量算子的循环实现 强相关,决定能否追上手写库 （TVM 论文）
搜索层 从海量合法实现里挑最优 与硬件绑定,但无需人为建模 （TVM 论文）

论文的贡献列表正是这三块: 张量表达式 + 新的调度原语、ML 驱动的自动优化框架、以及把它们与图级重写串起来的端到端栈。

3. 第一层: 图级优化(硬件无关,收益最大)

3.1 算子融合: 四类算子 + 三条规则

论文把图上的算子分为四类： injective(一对一映射,如 add)、reduction(归约,如 sum)、complex-out-fusable(可把逐元素映射融到其输出上,如 conv2d)、opaque(不可融合,如 sort)。对应的通用融合规则:

  1. 多个 injective 算子可以融合成另一个 injective 算子;
  2. reduction 算子可以和它的输入 injective 融合(如 scale + sum);
  3. conv2d 这类 complex-out-fusable 可以把输出端的逐元素算子融进自己。

收益（TVM 论文图 4）: 融合后算子相比未融合版本带来 1.2×–2× 的加速,原因是减少访存。测试负载: conv+bn+relu(128×28×28, 1×1×128×256)、depthwise-conv+bn+relu(512×14×14, 3×3×512)、rnn cell / lstm cell(hidden=128)。这套”四类 + 三规则”的价值在于它是可执行的判据 —— 评估一个推理引擎的融合能力时,可以直接问它覆盖了哪些类别与规则组合。

3.2 数据布局变换与静态内存规划

布局变换: 先为每个算子指定它在当前内存层级约束下的偏好布局,再在”生产者偏好 ≠ 消费者偏好”的边界上插入布局转换节点（TVM 论文）。典型例子是某类 DL 加速器原生做 4×4 矩阵操作,数据就要被切成 4×4 小块以获得访问局部性 —— 常见布局选择只是行主序 / 列主序,但真实部署里比这复杂得多。

静态内存规划: 该 pass 预先为每个中间张量分配内存,配合图级已知的固定输入形状(论文明确指出要利用”常见 DL 负载的形状特异性”)来压降峰值占用。

为什么这对部署人重要: 论文有一句话值得记住 —— 图级优化**”只和算子库提供的东西一样有效”。所以图优化收益大、硬件无关,是优先要做的**;算子级收益依赖后端,是必须能做的;而布局变换虽是”图级”手段,却直接决定访存效率 —— 这与端侧部署”先解决数据排布、再谈算术”的经验一致。

4. 第二层: 算子级 —— “计算与调度分离”

4.1 张量表达式: 只声明”算什么”

TVM 用张量表达式语言描述算子。与计算图不同,这里每个算子的实现不再是不透明的: 它被写成”输出张量的形状 + 每个元素的索引公式”（TVM 论文）。论文给的转置矩阵乘例子:

这段描述不含循环结构、不含线程组织、不含执行细节,只声明”算什么” —— 这正是 Halide 的 compute/schedule 分离思想（TVM 论文）。一个调度(schedule) = 从张量表达式到低层代码的具体映射,通过**增量施加保持语义等价的变换(调度原语)**来构造。用加速器上的矩阵乘举例: 同一份计算经不同调度步骤后变成完全不同的低层代码(先 tiling,再把中间结果缓存到加速器专用 buffer,最后用 tensorize 映射到 8×8 硬件矩阵指令)。

形式上,调度空间是”原语序列”的集合,论文 原文说优化器必须对真实负载搜索”数十亿(billions)”量级的配置:

$$
\mathcal{S} = {, s = (p_1, p_2, \dots, p_n) \mid \text{每个 } p_i \text{ 为保持语义的调度原语} ,}
\qquad |\mathcal{S}| \sim 10^{9}
$$

4.2 TVM 相对 Halide 新增的调度原语（TVM 论文图 6）

原语 来源 作用
Loop Transformations(分块 / 换序 / 展开…) Halide 局部性与并行
Thread Binding Halide 把循环绑到线程层次
Compute Locality Halide 计算局部性
Special Memory Scope TVM 共享内存 / 加速器片上内存的显式管理
Tensorization TVM 把计算模式匹配到硬件 intrinsic
Latency Hiding TVM TPU 类加速器专用,隐藏访存延迟
  • 嵌套并行 + 协作取数: 常见的”shared-nothing 嵌套并行”下,同一并行阶段内线程看不到兄弟线程的数据。TVM 引入 memory scope,允许把一个计算阶段标成 shared,让一组线程协作取数到共享内存,并由编译器自动插入 memory barrier。（TVM 论文图 7）在 Titan X 上用矩阵乘(规模 1024 / 2048)比较”含协作取数 / 不含协作取数 / cuBLAS”,含协作取数版本耗时最低。
  • Tensorization: 类比 SIMD 向量化,但指令输入是多维张量、长度固定或可变、各有不同数据布局;且不能只支持一组固定原语 —— 新加速器会带来自己的变体。TVM 把硬件 intrinsic 的声明与调度解耦: 用同一套张量表达式语言既声明 intrinsic 的行为、也声明 lowering 规则,然后由 tensorize 原语自动匹配计算模式并下沉到对应硬件指令。实测: 把移动 CPU 上的超低精度(1–2 bit)bit-serial 矩阵向量微内核以 tensor intrinsic 形式暴露给 TVM,相对未张量化版本最高 1.5× 加速。
  • 显式延迟隐藏: CPU 靠 SMT / 硬件预取隐式隐藏延迟,GPU 靠 warp 快速切换;TPU 类加速器采用 decoupled access-execute (DAE) 架构,把细粒度同步交给软件。TVM 引入 virtual threading 原语: 程序员按多线程的写法写(虚拟线程),编译器自动重写成单指令流 + 显式依赖入队 / 出队同步（TVM 论文图 8）。在 FPGA 加速器上跑 ResNet 各层,用 roofline 图对比开 / 关延迟隐藏: **峰值计算利用率从 70% 提升到 88%**。

5. 第三层: 自动调优 —— 用 ML 成本模型搜调度

论文里这套系统叫 automated optimizer / schedule explorer + ML-based cost model;”AutoTVM” 是它在后续 TVM 生态中的通行名字。

5.1 三条路线,为什么选”学习型”（TVM 论文表 1）

方法 数据需求 模型偏差 需要硬件信息 能从历史学习
黑盒自动调优 (blackbox auto-tuning) 高 无 否 否
预定义成本模型 (predefined cost model) 无 高 是 否
ML 成本模型 (ML based cost model) 低 低 否 是

黑盒调优(ATLAS / FFTW / TensorComprehensions 那一路)要跑很多次实验才能找到好配置,而一次真实测量是秒级的 —— 对十亿量级的空间不可行。预定义成本模型需要人为建模访存模式、数据复用、流水依赖、线程组织……而且每换一个硬件就得重建模型,工程负担巨大。ML 成本模型输入是 lowering 后的循环程序、输出是目标硬件上的预测运行时间,用户无需提供硬件细节,且随探索数据积累周期性更新,对相关负载的预测也更准。

5.2 模型、目标函数与速度约束

特征: 从循环程序里抽取 —— 每个循环层级上各 memory buffer 的访存次数与复用率(reuse ratio),以及循环标注的 one-hot 编码(vectorize / unroll / parallel 等)。候选模型有两类: 基于 XGBoost 的 gradient tree boosting,以及用 TreeRNN 直接对循环程序 AST 做摘要(免特征工程)。论文结论: 两者预测质量相当,但 tree boosting 预测速度快一倍、训练成本低得多,故选为默认成本模型。

速度约束(容易被忽略的判断): 搜索器会高频查询成本模型,因此”预测时间 + 重新拟合时间”必须远小于一次真实测量。这正是它区别于传统超参调优的地方 —— 后者测量代价极高,可以负担昂贵模型;这里测量是秒级,模型必须极快。实测: tree boosting 平均预测耗时 0.67 ms,比真实测量快数千倍（TVM 论文）。

目标函数: 搜索器只按预测值的相对次序(A 比 B 快)挑 top 候选,不预测绝对执行时间,因此用的是 rank objective（TVM 论文）。探索算法: “枚举 + 打分取 top-k”在大空间里不可行,改用并行模拟退火 —— 从随机配置出发随机游走到邻近配置,模型预测成本下降则接受,否则大概率拒绝;探索状态在模型更新后保留并从上次配置继续;无初始数据时随机采样去实测。分布式设备池与 RPC: 在主机编译、请求远端设备、远端运行、主机脚本取回结果,同一套接口既服务单算子调优也服务整图推理,且能跑交叉编译的模块 —— 论文强调这对嵌入式设备尤其关键,因为交叉编译、部署、测量传统上都是手工苦活。

5.3 成本模型 ≠ 基准测试(部署人视角)

  • 基准测试(benchmark): 在真实硬件上测量,给出真值;慢(秒级)、昂贵、不可穷举。
  • 成本模型(cost model): 对未测过的候选给预测,用来排序与剪枝;快(毫秒级)、可以错、只需保序正确。
  • 两者构成闭环: 模型预测 → 选一批候选 → 真实测量 → 数据回灌 → 模型更新。论文在 ResNet-18 的 conv2d 上(Titan X,最多 800 次试验)对比 ML 模型 / 黑盒遗传算法 / 随机搜索 / cuDNN 基线,结论是前者更快找到更好的配置;其说明还专门强调”ML 模型从没有任何训练数据开始,靠收集到的数据自我改进”。

对部署工程的启示: 手头的”分阶段计时 + 手工试参”其实就是黑盒调优,问题是只有真值、没有泛化。一旦有了”特征 → 预测”的映射,历史调优结果就能迁移到结构相似的新 shape / 新设备上 —— 这是这一层真正的增量。

VDLA 设计理论峰值 — 约 102.4 GOPS/s （TVM 论文）

服务器 GPU(Titan X；来源 TVM 论文): 对比 TVM / MXNet v1.1 / TensorFlow v1.7 / TensorFlow XLA;MXNet 与 TF 的卷积都用 cuDNN v7、矩阵乘用 cuBLAS v8,depthwise 卷积因较新 cuDNN 尚不支持、两家自己写了实现,XLA 走 JIT 编译。****: 端到端在 ResNet-18 / MobileNet / LSTM LM / DQN / DCGAN 五个负载上 加速 1.6×–3.8×,收益来自图级优化 + 自动优化器生成的融合算子叠加。原文解释: DQN 拿到 3.8× 是因为它用了非常规算子(4×4 conv2d,stride=2),cuDNN 对这些优化不好;而 ResNet 这类常规负载下 TVM 自动找到了优化实现 —— 常规负载拼工程,非常规负载才见编译器的价值。****(逐算子,额外加入 TensorComprehensions(TC, commit ef644ba),TC 结果取它每算子 10 代 × 100 群体 × 2 随机种子 = 2000 次试验中的最好 kernel;图中还含一个对 3×3 conv2d 做权重预变换 Winograd 的 TVM PT): 2D 卷积虽被 cuDNN 重度优化,TVM 仍在多数层生成更好的 GPU kernel;depthwise 卷积这类新算子,TVM 与 TC 都能相对 MXNet 的手写 kernel 找到快得多的实现。论文归因于”探索大调度空间 + 有效的 ML 搜索算法”。

嵌入式 CPU(ARM Cortex-A53,Quad Core 1.2 GHz；来源 TVM 论文): 基线 TensorFlow Lite(commit 7558b085)。(逐算子)/(端到端 ResNet-18 / MobileNet / DQN)显示 TVM 生成的算子超过 TFLite 手写优化版本**,论文以此说明 TVM 能快速优化新出现的张量算子(depthwise 卷积);脚注注明 DCGAN 与 LSTM 未给结果,因为基线尚不支持。超低精度: 针对 2-bit 激活 + 1-bit 权重推理,TVM 实现了一个 ARM 专用 tensorization intrinsic(bit-serial 矩阵向量微内核,位运算 + popcount 归约),再用自动优化器搜调度。** 对比 Caffe2(commit 39e07f7)的单线程手写超低精度库;因基线是单线程,论文同时给出单线程 TVM 对比,并指出 C5 / C3 是 1×1 卷积、计算强度低,多线程带来的加速较小;TVM 单线程在 C5、C8、C11(1×1 卷积、stride=2)上优势尤其明显,因为基线库没为这些形状做优化。此外 TVM 还能生成基线不支持的其它精度组合。

嵌入式 GPU(Firefly-RK3399 + ARM Mali-T860MP4；来源 TVM 论文): 基线 ARM Compute Library v18.03。****: 在三个可用模型、float16 与 float32 两种精度下都超过基线,加速 1.2×–1.6×;同样注明 DCGAN 与 LSTM 基线尚不支持。

FPGA 加速器 —— VDLA: 论文自建通用 DL 加速器原型 VDLA(Vanilla Deep Learning Accelerator),把此前多种加速器提案的特征提炼成极简架构,验证 TVM 对专用加速器的代码生成能力。硬件: 低功耗 PYNQ 板(含 ARM Cortex-A9 双核 @667 MHz + Artix-7 FPGA),片上 16×16 矩阵向量单元 @200 MHz,每周期完成 8-bit 相乘并累加到 32-bit 寄存器,理论峰值吞吐约 102.4 GOPS/s;片上分配 32 kB 激活存储 + 32 kB 参数存储 + 32 kB 微码 buffer + 128 kB 寄存器堆 —— 论文特意说明这些 buffer 远不足以装下一层 ResNet,因此正好构成”有效内存复用 + 延迟隐藏”的研究案例。工程成本: 为 VDLA 写 C runtime API 驱动库,新增这个专用加速器后端只花了约 2k LoC Python。端到端: ResNet 第一层因卷积深度太浅无法高效卸载、残差层与激活因 VDLA 不支持也留在 CPU,其余卷积层全部卸载;被卸载的卷积层获得 40× 加速(相对 Cortex-A9),但因 Amdahl 定律,整体性能被未能卸载的部分拖住。

7. 与后续生态的关系(本节为论文之后的演进,标注为”行业共识”)

7.1 TVM 内部的 IR 演进

论文里只有”计算图 + 张量表达式”两层,此后这套栈逐步分化:

时期 图级 IR 张量级 IR 说明
论文时期 计算图 + 图重写器 张量表达式 + 调度 的两级
之后 Relay(带类型的函数式图 IR,取代早期图 IR) TensorIR / TIR(以 TVMScript 书写,把”调度”第一类化) 表达控制流、动态形状更从容
近期(TVM Unity 方向) Relax(一等公民的符号形状) TensorIR 面向动态 shape 与端到端动态图

要点: 无论名字怎么换,“图级重写 + 循环级调度 + 自动搜索”这三段式结构没有变,这正是这篇论文留下的骨架。

7.2 与 Triton / TileLang 的定位差异

维度 TVM / Relax Triton TileLang
抽象粒度 张量表达式 → 循环级调度(可细到线程 / 内存 scope) block / 程序实例级(以 tile 为基本单位) tile 级 DSL(建于 TVMScript 之上)
谁来写调度 用户 / 模板 + 自动搜索 用户手写 Python 内核,编译器管布局与合并访存 用户写 tile 结构与流水,编译器管细节
主要目标 跨后端性能可移植(CPU / GPU / 加速器 / FPGA) 以 NVIDIA / AMD GPU 为主 以 GPU 高性能 kernel 为主
强项场景 算子库覆盖不全、后端多样、需端到端图级优化 快速写接近 cuBLAS 级别的 GPU kernel 显式表达流水 / tile,做 Attention、GEMM 类优化
典型关系 端到端编译器栈 常作为上层框架的 kernel 后端 借用 TVM 基础设施的 DSL 层

一句话定位: 本文确立的是”编译器做端到端 + 自动调优“的路线;Triton / TileLang 走的是”把 kernel 书写抽象抬高一档、但收敛到更少后端“的路线。两者不是替代关系,而是覆盖面 vs 表达力的不同取舍。

8. 速查卡与记忆口诀

问题 答案
论文要解决什么 图级优化够不到硬件、算子库只覆盖少数后端、手工调优不可移植
两级优化 图级(融合 / 布局 / 内存规划) + 算子级(张量表达式 + 调度)
融合的四类算子 injective / reduction / complex-out-fusable / opaque
计算与调度分离 继承自 Halide;TVM 增量 = 硬件 intrinsic 也从调度中解耦(tensorization)
TVM 新增的三个原语 Special Memory Scope、Tensorization、Latency Hiding
自动调优三路线 黑盒(数据需求高)/ 预定义模型(偏差高、需硬件信息)/ ML 模型(低数据、低偏差、能学历史)
默认成本模型 gradient tree boosting (XGBoost),预测 0.67 ms
搜索算法 并行模拟退火(rank objective,只排序不预测绝对值)
关键加速比 端到端 1.2×–3.8×;融合 1.2×–2×;张量化 1.5×;FPGA 卷积层 40×
关键利用率 延迟隐藏让峰值计算利用率 70% → 88%
部署三结论 ① 缺算子先查是否为融合派生物,DSL 生成可止损 ② 图级(融合 + 布局 + 内存)优先,收益大且硬件无关 ③ 区分成本模型(排序)与基准测试(定真值),手工试参只是黑盒调优

记忆口诀:

两级三层一闭环 —— 两级: 图级管结构(融合 / 布局 / 内存),算子级管循环(表达式 / 调度);三层: 图重写 → 调度空间 → 自动搜索;一闭环: 成本模型预测排序,真机测量回灌真值,二者往复。
三个”分离”: 计算与调度分离、intrinsic 与调度分离、预测与测量分离。
